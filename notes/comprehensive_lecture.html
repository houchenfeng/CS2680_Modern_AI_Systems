Part 1

Agentic Loop · Memory · Extending the Agent
AGENTIC LOOP

输入提示词后发生了什么？

传统 LLM 交互

  • 用户输入 → 模型生成 → 返回结果
  • 单轮对话，无状态
  • 模型无法主动执行操作

Agent 模式

  • 模型可以调用工具
  • 执行结果反馈给模型
  • 模型决定下一步行动
  • 循环直到任务完成
Agent = LLM + Tools + Loop
THREE STEPS

智能体循环的三个步骤

1. 模型推理
→
2. 工具调用
→
3. 结果反馈
→ 循环

模型推理

LLM 分析当前状态，决定下一步行动：生成文本 or 调用工具

工具调用

Harness 执行模型选择的工具（读文件、运行命令、搜索等）

结果反馈

工具执行结果添加到上下文，模型继续推理

EXAMPLE

实例：修复一个 Bug

  • 用户："修复 app.js 第 42 行的 TypeError"
  • Thought：需要先读取 app.js 查看第 42 行的代码
  • Action：read_file("app.js") → 发现 user.name.trim()，user 可能为 null
  • Thought：需要在调用前添加空值检查
  • Action：edit("app.js", old, new) → 添加 if (user) 保护
  • Observation：编辑成功 → 运行 npm test → 全部通过 ✓
    • 注意循环：Thought → Action → Observation → Thought → ... → 最终回答

    CONTEXT GROWTH

    上下文增长与压缩

    问题：上下文窗口有限

    • 每次工具调用都增加上下文
    • 长对话会超出窗口限制
    • 早期信息可能被截断

    解决：自动压缩

    • 接近限制时触发压缩
    • LLM 总结早期对话
    • 保留关键信息，丢弃细节
    • 用户可手动触发 /compact
    上下文使用: 45K / 200K tokens [=====> ] 22% 上下文使用: 180K / 200K tokens [=================>] 90% → 触发压缩 压缩后: 60K / 200K tokens [======> ] 30%

    代码风格约定

    • 注释要求

    CONCRETE EXAMPLE

    CLAUDE.md：Agent 记忆文件

    # Project: My Web App ## Build & Test Commands - Build: `npm run build` - Test all: `npm test` - Test single: `npm test -- -t "name"` - Lint: `npm run lint -- --fix` ## Code Style - TypeScript strict mode - Prefer functional components (React) - Use Zod for runtime validation - Error messages: sentence case, no period ## Memory Rules - After fixing a bug, record root cause in docs/decisions.md - Never repeat a fix that failed before - Check docs/decisions.md before debugging ## User Preferences - Reply in Chinese - Keep explanations under 3 sentences - Always run tests before committing

    CLAUDE.md 是什么？

    • 放在项目根目录的持久化记忆文件
    • 每次会话开始时自动加载到上下文
    • Agent 可以在会话中追加和修改
    • 跨会话保留项目知识和用户偏好

    关键设计

    • 纯文本：可 diff、可 git 追踪
    • 结构化：用 Markdown 标题分区
    • 可操作：写具体的命令和规则
    • 可演化：Agent 和用户共同维护
    BEST PRACTICES

    CLAUDE.md 实战：好 vs 坏

    ❌ 坏的写法

    # CLAUDE.md 写好代码。 注意性能。 项目用 React。 测试很重要。
    • 模糊、不可操作
    • 没有具体命令
    • Agent 无法执行

    ✅ 好的写法

    # Build & Test npm run build && npm test # Style TypeScript strict, 函数式组件 用 Zod 做运行时验证 # Pitfalls 不要修改 config/env.ts API key 从环境变量读取
    • 具体、可操作
    • 有命令和规则
    • Agent 可以直接使用

    SKILL STRUCTURE

    Skill 的结构

    # Skill: code-reviewer ## Description Review pull requests for bugs, style, and security issues. ## Tools - read_file(path) - list_dir(path) - search(pattern, glob) ## Instructions When reviewing a PR: 1. Read the diff carefully 2. Check for OWASP Top 10 issues 3. Verify error handling 4. Check test coverage 5. Output format: - 🔴 Critical: must fix - 🟡 Warning: should fix - 🟢 Suggestion: nice to have ## Constraints - Never modify code directly - Always cite file:line - Max 10 issues per review

    Skill 定义包含

    • Description：何时触发这个技能
    • Tools：允许使用的工具列表
    • Instructions：详细的执行步骤
    • Constraints：限制和边界

    加载方式

    • 用户显式调用 /code-reviewer
    • Agent 根据上下文自动选择
    • 只在需要时加载，节省上下文
    CONCRETE EXAMPLE

    skill.md：可复用的 Agent 技能

    # Skill: code-reviewer ## Description Review pull requests for bugs, style, and security issues. ## Tools - read_file(path) - list_dir(path) - search(pattern, glob) ## Instructions When reviewing a PR: 1. Read the diff carefully 2. Check for OWASP Top 10 issues: - SQL injection - XSS (unsanitized user input) - Hardcoded secrets 3. Verify error handling at system boundaries 4. Check test coverage for new code 5. Output format: - 🔴 Critical: must fix - 🟡 Warning: should fix - 🟢 Suggestion: nice to have ## Constraints - Never modify code directly - Always cite file:line for each issue - Max 10 issues per review

    skill.md 是什么？

    • 定义 Agent 的一项具体能力
    • 包含工具列表、执行步骤、输出格式
    • 可被不同 Agent 复用和组合
    • 类似"插件"但更轻量、更声明式

    与 CLAUDE.md 的区别

    • CLAUDE.md：项目级记忆，全局生效
    • skill.md：任务级能力，按需加载
    • CLAUDE.md 是"我知道什么"
    • skill.md 是"我能做什么"

    MCP：模型上下文协议

    MCP 是什么？

    • 标准协议：Agent 连接外部工具的接口
    • 类比：USB-C 之于硬件设备
    • 提供 Tools（操作）、Resources（数据）、Prompts（模板）
    • Agent 通过 MCP 调用数据库、文件系统、API 等

    三个核心抽象

    Tools
    Agent 可调用的函数
    Resources
    Agent 可读取的数据
    Prompts
    预定义的提示模板

    HOOKS

    Hooks：生命周期自动化

    什么是 Hooks？

    • 在特定事件发生时自动执行的脚本
    • 类似 Git Hooks 的概念
    • 无需 Agent 主动调用
    • 由 Harness 在后台触发

    常见 Hook 事件

    • pre-tool-call：工具调用前
    • post-tool-call：工具调用后
    • session-start：会话开始时
    • session-end：会话结束时
    // .claude/hooks/post-tool-call.sh #!/bin/bash # 每次文件修改后自动运行格式化 if [[ "$TOOL_NAME" == "write_file" || "$TOOL_NAME" == "edit" ]]; then npx prettier --write "$FILE_PATH" fi
    LIFECYCLE

    Hook 生命周期详解

    Harness 检测到事件
    →
    pre-tool-call Hook
    →
    执行工具
    →
    post-tool-call Hook

    pre-tool-call 用途

    • 参数验证：检查文件路径是否合法
    • 权限检查：确认是否允许执行此操作
    • 安全拦截：阻止危险命令（如 rm -rf）
    • 日志记录：记录即将执行的操作

    post-tool-call 用途

    • 自动格式化：文件修改后运行 Prettier
    • 类型检查：代码变更后运行 tsc
    • 测试验证：修改后自动运行相关测试
    • 结果处理：过滤或转换工具输出
    Hook 对 Agent 透明 — Agent 不需要知道 Hook 的存在
    PLUGINS

    Plugins：打包分发

    Plugin 包含什么？

    2. 限制工具集：code-reviewer 不需要 write_file，只给 read 和 search

    CASE STUDY

    案例：Caveman

    问题：上下文爆炸

    • 长对话消耗大量 tokens
    • API 成本高昂
    • 模型性能下降
    • 用户等待时间长

    Caveman 的解决方案

    • 双向压缩：输入和输出都压缩
    • 用 Plugin 打包压缩逻辑
    • Response Skill 让输出更简洁
    • 自动摘要早期对话
    核心思想：压缩 Agent 的 tokens，而不是压缩模型的能力
    COMPRESSION

    Caveman 双向压缩

    输入压缩

    • 自动摘要早期对话
    • 只保留关键决策和结果
    • 丢弃中间推理过程
    • 类似 /compact 但更智能

    输出压缩

    • Response Skill 约束输出格式
    • "用 3 句话回答"
    • "不要解释基础概念"
    • "直接给代码，不要注释"
    原始: 45K tokens → 压缩后: 12K tokens (73% 减少) 成本: $0.45 → $0.12 | 延迟: 8s → 2.5s

    ReAct Loop 回顾

    Thought
    →
    Action
    →
    Observation

    Thought 思考

    模型分析当前状态，推理下一步该做什么

    Action 行动

    调用工具执行操作（读文件、搜索、运行命令）

    Observation 观察

    工具返回结果，成为下一轮思考的输入

    ReAct = Reasoning + Acting，让模型边想边做
    FULL TRACE

    ReAct Loop 完整实例

  • 用户："找到并修复 utils.js 中的 bug"
  • Thought 1：需要先找到 utils.js 文件的位置
  • Action 1：glob("**/utils.js") → src/utils/utils.js
  • Thought 2：读取文件内容，查找可疑代码
  • Action 2：read_file("src/utils/utils.js") → 发现第 23 行 arr.sort() 没有比较函数
  • Thought 3：数字排序需要比较函数，应改为 arr.sort((a,b) => a-b)
  • Action 3：edit("src/utils/utils.js", old, new) → 修复成功
  • Observation：运行测试 → 全部通过 → 生成最终回答
    • AGENT LOOP

    Agent Loop 示意图

    用户输入
    →
    LLM 推理
    →
    工具调用
    →

    • 用户中断

    WORKFLOW

    编码任务流程实例

    任务："给 User 类添加 email 验证功能"

  • 搜索：glob("**/user.*") → 找到 src/models/user.ts
  • 搜索：grep("class User", "src/models/") → 定位类定义
  • 读取：read_file("src/models/user.ts") → 理解现有结构
  • 读取：read_file("src/models/user.test.ts") → 了解测试模式
  • 编辑：edit() → 添加 validateEmail() 方法
  • 编辑：edit() → 在构造函数中调用验证
  • 执行：bash("npm test -- user") → 验证测试通过
    • 搜索 → 读取 → 编辑 → 执行：工具组合使用完成复杂任务
    SEARCH

    搜索方法对比

    方法 适用场景 优点 缺点
    grep 精确文本匹配 快速、准确 需要知道关键词
    glob 文件名模式匹配 找到相关文件 只能匹配文件名
    find 复杂文件查找 灵活的条件组合 语法复杂
    语义搜索 概念查找 理解意图 需要向量索引
    最佳实践：先用 glob 定位文件，再用 grep 查找内容
    EDITING

    编辑方法对比

    write_file：全量写入

    • 覆盖整个文件
    • 适合创建新文件
    • 适合完全重写
    • 危险：会丢失未包含的内容

    edit：精确替换

    • 指定 old_string 和 new_string
    • 只修改匹配的部分
    • 更安全，不会意外删除
    • 推荐：大多数修改场景
    // edit 工具示例 old_string: "function add(a, b) { return a - b; }" new_string: "function add(a, b) { return a + b; }" // 只替换这一行，其他代码不受影响
    EXECUTION

    Shell 工具执行

    执行模式

    • 前台：等待命令完成
    • 后台：立即返回，稍后检查结果
    • 超时控制：防止无限等待

    安全考虑

    • 权限检查：哪些命令允许执行
    • 沙箱隔离：限制文件系统访问
    • 资源限制：CPU、内存、时间
    // 前台执行 bash("npm test") // 等待测试完成，返回输出 // 后台执行 bash("npm run dev", run_in_background=true) // 立即返回 // ... 稍后检查 ... bash("curl http://localhost:3000") // 验证服务启动
    BEST PRACTICES

    工具设计最佳实践

    1. 原子性：每个工具做一件事，做好它
    2. 明确的输入输出：参数类型清晰，返回值可预测
    3. 错误处理：失败时返回有用的错误信息，不是崩溃
    4. 幂等性：相同的输入产生相同的结果（尽可能）
    5. 最小权限：只给工具必要的访问权限
    6. 可组合：工具之间可以组合使用，解决复杂问题
    好的工具设计 = Agent 成功的一半
    CONTEXT

    从提示词工程到上下文工程

    提示词工程

    • 关注单次输入
    • 优化措辞和格式
    • 假设上下文固定
    • 适合单轮对话

    上下文工程

    • 关注整个上下文窗口
    • 管理信息的进入和退出
    • 动态调整上下文内容
    • 适合多轮 Agent 循环
    Agent 系统的核心挑战：在有限的上下文窗口中放入最相关的信息
    SCARCITY

    上下文是有限资源

    窗口大小限制

    • Claude: 200K tokens
    • GPT-4: 128K tokens
    • 看似很大，但很快用完
    • 长代码文件 = 数千 tokens

    性能影响

    • 上下文越长，推理越慢
    • 成本随 tokens 线性增长
    • 过长上下文降低准确性
    • "Lost in the Middle" 问题
    上下文使用策略： ✓ 准入：只让相关信息进入 ✓ 卸载：按需加载，用完即弃 ✓ 转换：压缩历史，保留要点 ✓ 压缩：LLM 总结作为最后手段
    EXAMPLE

    上下文管理：错误 vs 正确

    ❌ 错误做法

    • 一次性读取所有项目文件
    • 保留完整的工具调用历史
    • 把所有搜索结果塞入上下文
    • 不区分相关和不相关信息
    上下文占用：180K / 200K tokens 结果：响应变慢、准确性下降 "Lost in the Middle" 效应严重

    ✅ 正确做法

    • 按需加载：只读当前任务相关文件
    • 及时卸载：用完的工具结果立即丢弃
    • 摘要压缩：长对话用 LLM 总结
    • 分层管理：核心信息常驻，边缘信息按需
    上下文占用：45K / 200K tokens 结果：快速、准确、留有余量 关键信息始终在注意力范围内
    好的上下文管理 = 只让正确的信息在正确的时间出现在正确的地方
    ANATOMY

    上下文窗口的解剖

    系统提示词 (2-4K tokens) — 行为规则、工具定义
    记忆文件 (1-3K tokens) — CLAUDE.md、项目知识
    对话历史 (变化) — 之前的消息和工具调用结果
    当前输入 (变化) — 用户的最新请求
    预留空间 — 模型生成输出
    每一层都在争夺有限的空间，优先级管理至关重要
    MANAGEMENT

    管理上下文窗口的四种策略

    1. 准入 (Admission)

    守护入口：只让相关信息进入上下文

    • 按需加载文件，不要一次性读取全部
    • 使用搜索而非全量扫描

    2. 卸载 (Offloading)

    按需加载：用到时才放入上下文

    • Skill 只在需要时加载
    • 工具结果用完后可以丢弃

    3. 转换 (Transformation)

    选择性丢弃：压缩历史，保留要点

    • 自动摘要早期对话
    • 保留决策，丢弃推理过程

    4. 压缩 (Compression)

    LLM 总结：最后的手段

    • 用 LLM 总结长对话
    • 成本高，但在必要时有效

    Harness 框架

    • 上下文管理和优化

    • 我们可以改进的部分

    Agent Reliability · Error Compounding · Designing for Failure
    RELIABILITY

    为什么可靠性是个问题？

    错误复合效应

    每一步都有失败概率，多步任务失败率指数增长

    单步准确率: 95% 5 步任务: 0.95^5 = 77% 10 步任务: 0.95^10 = 60% 20 步任务: 0.95^20 = 36% 50 步任务: 0.95^50 = 8%

    现实世界的挑战

    • 工具调用可能失败
    • 模型可能产生幻觉
    • 上下文可能丢失关键信息
    • 环境可能变化（文件被删除）
    • 用户意图可能模糊
    Agent 系统必须在不确定性中可靠工作
    MATH

    错误复合效应：数学真相

    准确率 vs 任务步数

    单步准确率 p = 0.95 5步 → 0.95⁵ = 76.9% ✅ 10步 → 0.95¹⁰ = 59.9% ⚠️ 15步 → 0.95¹⁵ = 46.3% 🔴 20步 → 0.95²⁰ = 35.8% 🔴 30步 → 0.95³⁰ = 21.5% 💀 50步 → 0.95⁵⁰ = 7.7% 💀

    提升单步准确率的效果

    20步任务，不同单步准确率： p=0.90 → 12.2% 😰 p=0.95 → 35.8% 😟 p=0.98 → 66.8% 🙂 p=0.99 → 81.8% 😊 p=0.999→ 98.0% 🎉
    结论：提升每一步的可靠性比减少步数更重要 — 从 95% 到 99% 是质变

    • 权限不足
    • 资源限制（内存、磁盘）
    工具失败是最常见的故障来源 — 必须有重试和降级策略
    ENVIRONMENT

    环境失败

    外部变化

    • 文件被其他进程修改或删除
    • 网络中断或不稳定
    • 依赖服务宕机
    • 配置被更改

    资源限制

    • 磁盘空间不足
    • 内存耗尽
    • CPU 过载
    • 端口冲突

    权限问题

    文件权限变化、用户权限不足、沙箱限制

    并发冲突

    多个 Agent 同时修改同一资源

    DESIGN FOR FAILURE

    为失败而设计

    1. 重试策略

    • 指数退避重试
    • 最大重试次数
    • 区分可重试和不可重试错误

    2. 降级策略

    • 工具失败时使用备选方案
    • 部分失败时继续执行
    • 优雅降级而非完全失败

    3. 检查点

    • 保存中间状态
    • 可以从失败点恢复
    • 避免重复已完成的工作

    4. 验证和确认

    • 每步验证结果
    • 关键操作前确认
    • 输出格式检查

    5. 人类在环

    • 关键决策请求确认
    • 不确定时询问用户
    • 提供回退选项
