# 第二讲：Agent Use — 讲稿

## Slide 1 — 标题页

大家好，欢迎来到第二讲。今天我们要聊的主题是 **Agent Use**，也就是"如何使用 AI Agent"。

在上一讲中，我们了解了什么是 AI Agent、它和传统的 ChatGPT 有什么区别。今天，我们要从使用者的角度出发，真正理解像 Claude Code 这样的 Agentic Coding Tool 是怎么工作的。

你可能会想：我不就是打开终端、输入一句话、等它写代码吗？有什么好讲的？但实际上，当你按下回车键之后，背后发生的事情远比你想的复杂。今天我们就来揭开这层黑箱。

## Slide 2 — 课程大纲

这一讲的内容分为三个部分：

**第一部分：Agentic Loop**——这是整个 Agent 最核心的运行机制。我们会搞清楚：当你输入一句话之后，Claude 到底在做什么？它是怎么一步步完成任务的？

**第二部分：Memory**——Agent 怎么"记住"东西？它有两种记忆方式：一种是在一次对话中保持上下文的"工作记忆"，另一种是跨对话保存的"持久记忆"。我们会详细讲这两种记忆是怎么工作的。

**第三部分：Extending the Agent**——Agent 本身的能力是有限的，但我们可以通过各种方式扩展它。比如给它接入外部工具、教它新的工作流程、在特定事件发生时自动执行操作等等。

这三部分层层递进：先理解核心循环，再看记忆系统，最后看如何扩展。

## Slide 3 — 课程目标

学完这一讲之后，你应该能做到四件事：

第一，**Trace（追踪）** 一个 Agentic Session 的完整生命周期。也就是说，从你输入一句话开始，到最终得到结果，你能说清楚中间每一步发生了什么。

第二，**Explain（解释）** Agent 的记忆和上下文系统是怎么工作的。为什么 Agent 有时候会"忘记"之前说过的话？怎么让它记住重要的东西？

第三，**Diagnose（诊断）** 常见的 Agent 使用问题。比如 Agent 突然不干活了、输出质量变差了、或者做了你不想要的事情——你能分析出原因。

第四，**Extend（扩展）** Agent 的能力。通过 Skills、MCP、Hooks、Plugins 这些机制，让 Agent 能做更多事情。

## Slide 4 — 从一个真实问题开始

让我们从一个大家可能都遇到过的问题开始：

> "Claude 是怎么把我的 Git 仓库搞乱的？"

这个问题很真实。你可能让 Claude Code 帮你改个 bug，结果它不但改了 bug，还顺手重构了一堆你不打算动的文件，甚至创建了几个新文件。你一看 git status，一片红。

为什么会这样？因为 Claude 在默认情况下有相当大的自主权。它可以读文件、写文件、执行命令。如果你不给它设定边界，它就会按照自己对任务的理解去行动——而它的理解可能和你的预期不完全一致。

这个问题的根源在于：你不了解 Agent 的"行为边界"是怎么设定的。今天我们就来搞清楚这件事。

## Slide 5 — Context Engineering 的概念

在深入技术细节之前，我们先建立一个思维框架。

大家可能听说过 **Prompt Engineering**（提示工程）。Prompt Engineering 的核心思想是：你给 LLM 的输入文本（也就是 prompt）的质量，直接决定了输出质量。所以你要精心设计你的 prompt。

但当我们面对的是一个 Agent 的时候，仅仅设计好用户输入的那句话是不够的。Agent 在收到你的消息之前，已经加载了大量的上下文信息：系统指令、项目配置、记忆、工具列表等等。

所以我们需要一个更全面的概念——**Context Engineering**（上下文工程）。它的意思是：你要设计的不只是用户输入的那句话，而是 Agent 在做出决策时能看到的**所有信息**。

这就像冰山一样：用户输入的那句话只是露出水面的一小部分，水面下还有巨大的上下文在影响着 Agent 的行为。

---

## Slide 6 — Agent 看到的全部上下文

那么 Agent 在做决策时，到底能看到哪些信息呢？

让我们看这张图。从下往上看：

**最底层是 User Turn**——就是你输入的那句话。这是你直接控制的部分，也是传统 Prompt Engineering 关注的重点。

**往上是 Conversation History**——也就是对话历史。你和 Agent 之前的所有对话内容都会作为上下文传给模型。对话越长，上下文越大。

**再往上是各种持久化的上下文层**：
- **System Prompt**：系统指令，定义了 Agent 的基本行为方式
- **CLAUDE.md files**：项目级别的指令文件，告诉 Agent 这个项目的特殊规则
- **Memory**：Agent 的记忆系统，保存跨会话的知识
- **Tool Definitions**：Agent 可以使用的工具的定义
- **Skills / MCP**：更高级的扩展能力

**最顶层是 Session State**——当前会话的状态，包括当前工作目录、环境变量等。

关键点在于：**Agent 的每一次行动，都是基于它能看到的这些全部上下文做出的决策**。所以，如果你想让 Agent 表现得好，你需要管理好这所有的层——这就是 Context Engineering。

## Slide 7 — Agentic Loop 的核心循环

现在我们进入第一部分的核心：**Agentic Loop**。

这是 Claude Code 最基本的运行机制。整个 Agent 的工作可以归纳为一个不断重复的循环，包含三个阶段：

**第一步：Gather Context（收集上下文）**
Agent 接收当前所有的上下文信息——包括你的输入、对话历史、系统指令、工具列表等。

**第二步：Generate Action（生成行动）**
基于这些上下文，LLM 进行推理（reasoning），决定下一步应该做什么。可能是读一个文件、执行一条命令、编辑一段代码，或者直接回复你。

**第三步：Run Tool（执行工具）**
Agent 的运行时环境（我们叫它 **Harness**）负责执行 LLM 决定的操作，然后把结果返回给模型。

然后循环回到第一步，模型看到工具执行的结果，再决定下一步做什么。

这个循环会一直持续，直到 Agent 认为任务完成了，给你返回最终的文本回复。

---

## Slide 8 — Model Proposes, Harness Executes

这里有一个非常重要的架构原则：**Model Proposes, Harness Executes**（模型提议，运行时执行）。

这是什么意思呢？Claude 这个语言模型本身并不能直接操作你的文件系统、不能执行命令、不能读写文件。它只能生成文本。

但是，Claude 可以生成一种特殊格式的输出，表达"我想要做某件事"的意图——比如"我想读取 foo.py 这个文件"或者"我想执行 git status 命令"。

然后，**Harness**（运行时环境，也就是 Claude Code 这个程序本身）会接收到这个请求，检查权限，确认安全，然后真正去执行这个操作，再把执行结果喂回给模型。

所以分工是这样的：
- **Model（模型）**：负责思考和决策——"我应该做什么"
- **Harness（运行时）**：负责执行和把关——"能不能做、怎么做"

这个设计很重要，因为它意味着：模型的建议不一定会被执行。中间有一个权限检查的环节。这就是为什么我们有不同的 Permission Mode。

---

## Slide 9 — Permission Modes（权限模式）

在 Harness 执行模型的请求之前，会经过一个 **Permissions Layer**（权限层）。Claude Code 提供了四种权限模式，控制 Agent 的自主程度：

**Manual（手动模式）**：每一个操作都需要你手动批准。最安全，但也最慢。Agent 想读个文件都要你点确认。

**Accept Edits（接受编辑模式）**：自动批准文件的读写操作，但执行命令（比如 shell 命令）仍然需要你确认。这是一个比较常用的平衡点。

**Bypass Permissions（绕过权限模式）**：除了少数危险操作（比如修改系统文件），其他操作都自动批准。适合你信任 Agent 的场景。

**Auto（全自动模式）**：所有操作都自动批准，包括通常被认为是危险的操作。这是最激进的模式，适合在沙箱环境或者你完全信任任务的场景下使用。

这四种模式给你的控制粒度是不同的。选择哪种模式，取决于你对当前任务的信任程度。

## Slide 10 — Agentic Loop 的详细流程

让我们更细致地走一遍这个循环。

假设你对 Claude Code 说："帮我修复 auth.py 里的一个 bug"。

**第一轮循环：**
1. 模型收到你的消息，加上所有上下文（系统指令、项目配置等）
2. 模型推理：我需要先看看 auth.py 的内容才能找到 bug
3. 模型发出请求：Read("auth.py")
4. Harness 检查权限，确认可以读文件
5. 执行读取，把文件内容返回给模型

**第二轮循环：**
1. 模型看到了 auth.py 的内容
2. 模型推理：第42行有个逻辑错误，我需要修复它
3. 模型发出请求：Edit("auth.py", 修改第42行)
4. Harness 检查权限，确认可以编辑
5. 执行编辑，返回结果

**第三轮循环：**
1. 模型看到编辑成功了
2. 模型推理：我应该运行测试确认修复有效
3. 模型发出请求：Bash("python test_auth.py")
4. Harness 检查权限，执行命令
5. 测试通过了

**第四轮循环：**
1. 模型看到测试通过
2. 模型推理：任务完成了，告诉用户
3. 模型生成文本回复："已修复 auth.py 第42行的 bug，测试通过"

这就是一个完整的 Agentic Session。注意，模型不是一次性规划好所有步骤的——它是**一步一步走**的，每一步都根据上一步的结果来决定下一步做什么。

## Slide 11 — 推理链的结构

这张图展示了推理链（Reasoning Chain）的结构。

整个过程可以表示为：**U → M₁ → T₁ → M₂ → T₂ → ... → Mₙ → A**

其中：
- **U** 是 User Input（用户输入）
- **M** 是 Model Inference（模型推理），也就是模型思考和决策的过程
- **T** 是 Tool Execution（工具执行），也就是 Harness 实际执行操作
- **A** 是 Final Answer（最终回答）

它们是交替出现的：模型推理一次，执行一个工具；再推理一次，再执行一个工具……直到模型认为任务完成，输出最终回答。

这里有几个重要的观察：

**第一**，每一步推理（M）都是基于之前所有的轨迹（trajectory）——包括用户输入、所有工具的执行结果。所以上下文会随着循环越来越长。

**第二**，模型每次推理时，它看到的"窗口"是有限的。这就是为什么 Context Window（上下文窗口）的大小很重要。当对话太长，早期的内容可能会被压缩或丢失。

**第三**，推理链的长度（也就是循环的次数）直接决定了任务的成本和延迟。循环越多，花的钱越多，等的时间越长。

---

## Slide 12 — 工具如何变成代码执行

这张图展示了一个更具体的例子：模型怎么通过工具调用来执行代码。

当模型决定要执行一段 Python 代码时，实际发生的事情是：

1. 模型生成一个 **tool_use** 格式的请求，比如 `{"command": "python script.py"}`
2. Harness 接收到这个请求
3. Harness 做 **Permission Check**（权限检查）：这个操作允许吗？
4. 如果允许，Harness 执行 **Tool Execution**（工具执行）：真正运行这条命令
5. 得到结果后，Harness 把结果以 **tool_result** 的格式返回给模型
6. 模型看到结果，继续推理

关键概念：模型从来不"直接"执行代码。它只是发出一个"我想执行这段代码"的请求。真正的执行权在 Harness 手里。这就是前面说的 **Model Proposes, Harness Executes** 原则的具体体现。

这个设计带来了一个重要的安全特性：在任何一步，Harness 都可以拒绝执行模型的请求。这就是权限系统发挥作用的地方。

## Slide 16 — 上下文管理（Context Management）

现在我们来聊一个非常实际的问题：**上下文管理**。

前面我们说 Agent 做决策时依赖所有能看到的上下文。但问题是，上下文不是免费的。

**首先，上下文窗口是有限的。** 即使是最大的模型，也有 token 数量的上限。当对话变长，早期的内容可能放不下了。

**其次，上下文是有成本的。** 每一轮循环，所有的上下文都要重新传给模型。上下文越大，推理越慢、花费越多。

**最后，上下文的质量影响决策的质量。** 如果上下文里充满了无关信息，模型可能会被"噪音"干扰，做出不好的决策。

所以上下文管理的核心挑战是：**在有限的窗口里，放入最有价值的信息**。

---

## Slide 17 — Context Compaction（上下文压缩）

当对话变得太长，快要超出上下文窗口的时候，系统会触发一个叫 **Context Compaction**（上下文压缩）的机制。

它做的事情是：把早期的对话内容**总结**成一段简短的摘要，用摘要替换掉原始的详细内容。

但是，压缩不是简单地把所有内容都总结一遍。有几样东西在压缩过程中会被**重新注入**，确保它们不会丢失：

- **CLAUDE.md**：项目指令文件会被重新加载，确保项目规则不会因为在压缩中被丢掉
- **Memory**：Agent 的记忆也会被重新注入
- **Tool Definitions**：工具的定义会保留，否则 Agent 就不知道自己有什么工具可用了

你可以把 Context Compaction 想象成：你在做笔记的时候，发现笔记本快写满了，于是你把前面几页的内容写了个摘要，腾出空间写新的内容。但你的"规则手册"（CLAUDE.md）和"记忆卡片"（Memory）会重新抄一遍，确保不会丢。

---

## Slide 18 — 按需加载（Demand-Driven Access）

Agent 并不会一开始就把整个代码仓库都加载到上下文里——那是不可能的，一个大型项目可能有几百万行代码。

那它怎么访问代码呢？答案是 **Demand-Driven Access**（按需访问）。

代码仓库静静地待在磁盘上。Agent 需要的时候，通过 **Grep**（搜索）和 **Read**（读取）这两个工具，按需拉取（pull）它需要的那部分代码。

就像你去图书馆找资料：你不需要把整个图书馆的书搬回家，你只需要找到你要的那几页，复印下来看。看完了如果需要更多，再去复印。

这种设计的好处是：上下文里只包含当前任务真正需要的信息，不会被无关代码淹没。

---

## Slide 19 — Agent Memory 的两种类型

现在我们进入 **Memory**（记忆）系统。

Agent 有两种截然不同的记忆：

**Context（上下文记忆 / 工作记忆）**：
- 就是当前对话中的所有消息——你说的话、Agent 的回复、工具的执行结果
- 它存在于内存中，随着对话进行不断增长
- 当对话结束（session 结束），这些记忆就**消失**了
- 好处是：即时可用，模型每次推理都能看到
- 坏处是：会消失，而且有大小限制

**Persistent Memory（持久记忆）**：
- 保存在磁盘上，不会因为对话结束而丢失
- 下次开新对话时，可以被重新加载
- 好处是：跨会话存活，能积累知识
- 坏处是：需要显式地写入和读取，不是自动就能用的

你可以这样类比：Context 就像你的**工作记忆**——你正在做的事情都记在脑子里，但睡一觉可能就忘了。Persistent Memory 就像你的**笔记本**——你写下来的东西，明天、下周、明年都还能翻出来看。

---

## Slide 20 — 持久记忆的两种机制

Persistent Memory 具体怎么实现呢？在 Claude Code 里，有两种机制：

**第一种：CLAUDE.md Files**
这是一个特殊的 Markdown 文件，你可以放在不同的位置。Agent 在每次会话开始时会自动读取它。你可以在里面写项目的规则、常用命令、编码风格偏好等等。

**第二种：Auto Memory**
这是 Agent 自动管理的记忆系统。Agent 可以在对话过程中主动把重要的信息保存到记忆文件中，下次会话时自动加载索引。

这两种机制可以配合使用。CLAUDE.md 更适合写那些"永远不变"的项目规则；Auto Memory 更适合记录那些在使用过程中逐渐积累的知识。

---

## Slide 21 — CLAUDE.md 的作用和位置

**CLAUDE.md** 是 Claude Code 的一个特殊配置文件。它的作用是：给 Agent 提供关于这个项目的持久化指令。

你可以把它理解为"给 Agent 的项目说明书"。

CLAUDE.md 可以放在四个不同的位置，每个位置有不同的作用范围和优先级：

**Managed Policy（管理策略）**：由企业/组织统一管理。比如公司规定"所有项目都不允许使用某个库"，这种规则放在这里。优先级最高。

**User Instructions（用户指令）**：放在用户主目录下（`~/.claude/CLAUDE.md`）。这是你个人的偏好，对所有项目生效。比如"我喜欢用单引号不用双引号"。

**Project Instructions（项目指令）**：放在项目根目录下（`项目根/CLAUDE.md`）。这是项目级别的规则，对所有使用这个项目的人生效。比如"这个项目用 pnpm 不用 npm"。会被提交到 Git 里，团队共享。

**Local Instructions（本地指令）**：放在项目根目录下的 `.claude/CLAUDE.md`。这是你个人的项目级偏好，不会被提交到 Git。比如"我本地开发时用这个端口号"。

优先级从高到低：Managed > User > Project > Local。

---

## Slide 22 — CLAUDE.md 应该写什么

CLAUDE.md 不是什么都适合往里写的。这里有一些指导原则：

**适合写的（High Signal）**：
- **常用命令**：比如怎么构建、怎么测试、怎么部署。Agent 经常需要运行这些命令，写在这里它就不用猜了
- **硬性约束**：比如"绝对不要修改 database schema"、"不要使用 any 类型"。这些是模型不容易从代码里推断出来的规则
- **事实性信息**：比如"这个项目的 API 文档在 docs/api.md"、"部署需要先跑 migration"

**不适合写的（Low Signal / No Signal）**：
- **模型已经知道的东西**：比如"Python 是一种编程语言"——这不用说，模型当然知道
- **Lint 工具能检查的东西**：比如"变量名用 camelCase"——这种规则应该交给 ESLint 之类的工具去强制执行，写在 CLAUDE.md 里是浪费上下文
- **长篇大论的说明**：CLAUDE.md 会被加载到每一次对话的上下文中。如果你写了十页纸，那每次对话都要消耗十页纸的 token。保持精简

## Slide 23 — .claude/rules/ 目录

如果你发现你的 CLAUDE.md 越写越长，内容越来越多，那你可以用 **.claude/rules/** 目录来组织它。

这个目录的思想是：把一个大而全的 CLAUDE.md 拆分成多个小而专注的规则文件。

比如：
- `.claude/rules/testing.md`——测试相关的规则
- `.claude/rules/style.md`——代码风格相关的规则
- `.claude/rules/deployment.md`——部署相关的规则

更厉害的是，每个规则文件可以在 **frontmatter**（文件头部的元数据）里指定 `paths`，说明这条规则只在操作特定路径的文件时才生效。

比如 testing.md 可以设置 `paths: ["src/**/*.test.ts"]`，意思是：只有当 Agent 在操作测试文件时，才加载这条规则。

这样做的好处是 **Lazy Loading**（延迟加载）——不是所有规则都一股脑加载到上下文里，而是按需加载。这大大节省了上下文空间。

---

## Slide 24 — Auto Memory 系统

现在我们来详细讲 **Auto Memory**——Agent 的自动记忆系统。

和 CLAUDE.md 不同，Auto Memory 不需要你手动去维护。Agent 可以在对话过程中自动地把重要信息保存到记忆文件里。

Auto Memory 的记忆文件存放在特定目录下：`~/.claude/projects/<project-path>/memory/`

每个记忆文件都有一个 **Frontmatter**（前置元数据），包含：
- **name**：记忆的名称
- **description**：记忆的描述——这很重要，因为 Agent 在决定是否读取一条记忆时，首先看的就是描述
- **type**：记忆的类型

记忆系统还有一个 **MEMORY.md** 索引文件。这个索引文件在每次会话开始时都会被加载到上下文里，Agent 通过它来知道"我有哪些记忆"。

---

## Slide 25 — Memory 的四种类型

Auto Memory 把记忆分成四种类型，每种类型有不同的用途：

**user（用户信息）**：
记录关于用户本人的信息。比如用户的角色、技术栈偏好、工作经验等。这样 Agent 可以根据用户的水平调整回答的深度。

**feedback（反馈信息）**：
记录用户对 Agent 行为的纠正或肯定。比如"不要在没有我确认的情况下删除文件"或者"上次那种分步骤的方式很好，继续保持"。这让 Agent 能不断改进和你的协作方式。

**project（项目信息）**：
记录关于当前项目的动态信息。比如"下周要发布 2.0 版本"、"数据库迁移脚本已经跑完了"。这些信息不在代码里，但对理解项目上下文很重要。

**reference（参考信息）**：
记录外部资源的指向。比如"API 文档在 confluence 的这个页面"、"设计稿在 Figma 的这个链接"。

---

## Slide 26 — Memory 的检索机制

记忆是怎么被使用的呢？这里有一个关键的设计：**Lazy Loading**（延迟加载）。

**MEMORY.md 索引文件**是始终被加载到上下文中的。它就像一本书的目录——Agent 始终能看到目录。

但具体的记忆内容（各个 topic 文件）**不会**一开始就全部加载。只有当 Agent 判断某条记忆和当前任务相关时，它才会去读取那条记忆的完整内容。

这种设计的原因很实际：如果你有 100 条记忆，每条都很长，全部加载到上下文里会浪费大量 token。通过延迟加载，Agent 只在需要的时候才付出这个成本。

你可以类比手机上的通讯录：你始终能看到所有联系人的名字（索引），但只有当你需要联系某个人时，才会打开他的详细资料。

---

## Slide 27 — Memory 相关的命令

Claude Code 提供了一些命令来管理记忆：

**/memory**：手动触发记忆保存。你可以用这个命令告诉 Agent"把刚才这件事记下来"。

**/context**：查看当前上下文的组成。你可以看到上下文里都有什么、占了多少空间。

**/init**：初始化项目。这会在项目根目录创建一个 CLAUDE.md 的初始模板，帮你快速开始。

**/doctor**：诊断工具。检查 Agent 的配置是否正常、有没有什么问题。

这些命令让你对记忆系统有更多的控制权。

---

## Slide 28 — 记忆的成本

这张 slide 提出了一个很有哲理的观点：

> "Context is rented, memory is owned."
> （上下文是租来的，记忆是拥有的。）

什么意思呢？

**Context（上下文）** 是临时的。每次会话结束，对话的上下文就消失了。而且上下文窗口是有限的——你在里面放了太多东西，就必须压缩、丢弃一些。所以上下文是"租来的空间"，你用完了就要还回去。

**Memory（记忆）** 是持久的。你写入记忆文件的东西，会一直在那里，直到你主动删除。所以记忆是"你拥有的资产"。

但紧接着有一个警告：**Stale memory is worse than no memory**（过时的记忆比没有记忆更糟）。

为什么？因为没有记忆，Agent 会从头开始了解情况，至少不会犯错。但如果有一条过时的记忆——比如"这个项目用的是 PostgreSQL 12"，但实际上已经升级到 PostgreSQL 15 了——Agent 就会基于错误的信息做出错误的决策。

所以，要定期清理和更新你的记忆。记忆不是越多越好，而是越准确越好。

---

## Slide 29 — 核心工具（Tools）

现在我们进入工具的部分。Agent 的能力来自于它能使用的工具。

Claude Code 有六类核心工具：

**Read（读取）**：读取文件内容。Agent 通过它来了解代码长什么样。

**Search（搜索）**：包括 **Grep**（按内容搜索）和 **Glob**（按文件名搜索）。当 Agent 不知道某个东西在哪个文件里时，它先搜索。

**Fetch（获取）**：从外部获取信息，比如访问网页。

**Edit / Write（编辑/写入）**：修改现有文件或者创建新文件。这是 Agent 修改代码的主要方式。

**Shell（命令行）**：执行终端命令。比如运行测试、安装依赖、执行 git 操作等。

**Delegate（委派）**：把子任务委派给另一个 Agent 实例。这在处理复杂任务时很有用——主 Agent 可以把一些独立的工作分配给子 Agent 并行处理。

这些工具组合起来，让 Agent 能够完成几乎所有的编程任务。

---

## Slide 31 — 扩展 Agent

Agent 内置的工具虽然强大，但有时候不够用。比如：

- 你想让 Agent 直接操作 GitHub 的 Pull Request——内置工具做不到
- 你想让 Agent 在每次保存文件后自动运行格式化——内置工具没有这种"事件触发"的能力
- 你想让 Agent 了解你们团队特定的开发流程——它天生不知道

所以 Claude Code 提供了四种扩展机制。让我们逐一了解。

---

## Slide 32 — 四种扩展机制概览

这四种扩展机制分别是：

**Skills（技能）**：教 Agent 怎么做某件事。是"怎么做"（How）的知识。

**MCP（Model Context Protocol）**：给 Agent 接入外部服务。是 Agent 的"手"，让它能触达外部世界。

**Hooks（钩子）**：在特定事件发生时自动执行操作。是"当 X 发生时，自动做 Y"的自动化。

**Plugins（插件）**：把 Skills、Hooks、MCP 配置打包在一起的可安装包。是分发和复用的载体。

这四种机制可以单独使用，也可以组合使用。接下来我们一个一个详细讲。

---

## Slide 33 — Skills（技能）

**Skill** 是什么？简单说，Skill 就是一份"操作手册"，教 Agent 怎么做某一类特定的事情。

你可能会问：Agent 不是已经很聪明了吗？为什么还需要教它？

原因是：Agent 虽然通用能力很强，但对于一些特定的、有固定流程的任务，如果没有明确的指导，它可能会走弯路。比如你们团队有一个特定的部署流程，涉及五个步骤、三个工具。Agent 可能不知道这个流程，或者做得不对。

Skill 的作用就是：**把领域知识、参考资料、可重复的工作流封装起来**，让 Agent 在需要的时候可以参考。

从本质上说，Skill 是一种 **Context Engineering**——你在 Agent 需要的时候，把正确的上下文信息提供给它。

---

## Slide 34 — Skill 的结构

一个 Skill 的文件结构是这样的：

```
.claude/skills/<skill-name>/
├── SKILL.md          # 核心指令文件
├── references/       # 参考资料
│   └── *.md
└── scripts/          # 辅助脚本
    └── *.py / *.sh
```

**SKILL.md** 是核心——里面写了这个 Skill 的指令，告诉 Agent 应该怎么做。

**references/** 目录存放参考资料——比如 API 文档、规范说明等。Agent 在需要时可以查阅。

**scripts/** 目录存放辅助脚本——比如自动化测试脚本、数据处理脚本等。

Skill 可以放在三个位置：
- **用户级**（`~/.claude/skills/`）：你个人使用，所有项目都能用
- **项目级**（`.claude/skills/`）：项目级别的 Skill，团队共享
- **插件级**（通过 Plugin 分发）：随插件安装

---

## Slide 35 — Skill 的调用方式

Skill 有两种调用方式：

**Model-Invoked（模型调用）**：
Agent 在推理过程中，自己判断需要使用某个 Skill，然后自动加载它。你不需要做任何事情——Agent 会根据 Skill 的描述，判断当前任务是否匹配。

**User-Invoked（用户调用）**：
你通过输入 `/skill-name` 来手动触发一个 Skill。比如 `/deploy` 就会触发部署相关的 Skill。

这两种方式有一个重要的区别：**上下文成本**。

当一个 Skill 被加载时，它的 SKILL.md 内容会被注入到上下文中。这会占用上下文空间。所以，不是 Skill 越多越好——每个 Skill 都有成本。

这也是为什么 Skill 的描述（description）很重要：它帮助 Agent 判断什么时候需要加载这个 Skill，避免不必要的加载。

---

## Slide 36 — MCP（Model Context Protocol）

**MCP** 全称是 **Model Context Protocol**（模型上下文协议）。

如果说 Skill 是教 Agent "怎么做"，那 MCP 就是给 Agent "新的手"。

具体来说，MCP 是一个标准化的协议，让 Agent 能够连接到各种外部服务。比如：

- 连接 **GitHub**：让 Agent 能创建 PR、查看 Issue、管理 Repository
- 连接 **Database**：让 Agent 能查询数据库
- 连接 **Slack**：让 Agent 能发消息
- 连接 **Figma**：让 Agent 能读取设计稿
- 连接 **Browser**：让 Agent 能浏览网页

有了 MCP，Agent 的能力不再局限于本地文件系统。它可以触达（reach into）任何通过 MCP 接入的外部服务。

---

## Slide 37 — MCP 的工作原理

MCP 的工作方式可以这样理解：

**没有 MCP 的时候**：Agent 只能使用内置的工具（Read、Write、Shell 等）。它就像一个只能用手边工具干活的人。

**有了 MCP 之后**：Agent 可以通过标准协议调用外部服务。就像给它接上了各种"遥控器"——它按一下 GitHub 遥控器的按钮，GitHub 那边就执行对应的操作。

MCP 是一个**双向协议**：
- Agent 通过 MCP 向外部服务发送请求（比如"创建一个 PR"）
- 外部服务通过 MCP 返回结果（比如"PR 创建成功，链接是..."）

这种设计的好处是**标准化**。不管接入的是什么服务，对 Agent 来说调用方式都是一样的。你不需要为每个服务写不同的集成代码。

---

## Slide 38 — MCP 的实际例子

让我们看几个具体的 MCP 使用场景：

**场景一：GitHub 集成**
你可以通过 MCP 让 Agent 直接操作 GitHub。比如你说"帮我为这个 branch 创建一个 PR"，Agent 就能通过 GitHub MCP 直接创建，不需要你手动去网页上操作。

**场景二：浏览器自动化**
通过 Browser MCP，Agent 可以打开网页、点击按钮、填写表单。这在测试 Web 应用时非常有用。

**场景三：数据库查询**
通过 Database MCP，Agent 可以直接查询数据库，帮你分析数据或者验证数据是否正确。

这些场景的共同点是：Agent 的能力通过 MCP 延伸到了本地文件系统之外。

---

## Slide 39 — Hooks（钩子）

**Hook** 是第三种扩展机制。

如果说 Skill 是"教 Agent 怎么做"，MCP 是"给 Agent 新的手"，那 Hook 就是"在特定时刻自动触发操作"。

Hook 的核心思想是：**Lifecycle Automation**（生命周期自动化）。

你可以设定：当某个特定事件发生时，自动执行某些操作。这不需要 Agent 的推理——它是硬编码的自动化规则。

比如：
- "每次 Agent 要执行 shell 命令之前，先检查命令是否安全"
- "每次 Agent 完成一个任务后，自动运行 lint 检查"
- "每次会话开始时，自动加载某些环境变量"

这些都是 Hook 可以做到的。

---

## Slide 40 — Hook 的触发时机

Hook 可以在五个不同的时机触发：

**Session Start（会话开始）**：当你启动一个新的 Claude Code 会话时触发。可以用来初始化环境。

**User Prompt（用户输入）**：当你发送一条消息给 Agent 时触发。可以用来对你的输入做预处理或检查。

**Tool Call（工具调用前）**：在 Agent 调用某个工具之前触发。可以用来拦截危险操作——比如 Agent 想执行 `rm -rf`，Hook 可以先检查并阻止。

**Tool Result（工具返回后）**：在工具执行完毕、结果返回给模型之前触发。可以用来对工具的输出做后处理。

**Stop（停止时）**：在 Agent 完成任务、准备停止时触发。可以用来做清理工作或者运行最终检查。

每个 Hook 可以执行的操作包括：运行 Shell 命令、发送 HTTP 请求、调用 MCP 工具、显示提示信息、甚至启动一个子 Agent。

---

## Slide 41 — Plugins（插件）

**Plugin** 是第四种扩展机制，也是最"高层"的一个。

Plugin 是什么？简单说，它是一个**打包和分发的单元**。

一个 Plugin 可以把前面讲的三种扩展机制打包在一起：
- 几个 **Skills**
- 几个 **Hooks**
- 一些 **Agent** 定义
- 一些 **MCP** 配置

然后，整个 Plugin 可以作为一个整体被安装、卸载、版本管理、分发给团队。

如果说 Skill 是一道菜的做法，MCP 是一种厨具，Hook 是一个定时器，那 Plugin 就是一个"料理包"——把所有东西打包在一起，开箱即用。

---

## Slide 42 — Plugin 的价值

Plugin 解决的核心问题是：**复用和分发**。

想象一下：你花了很多时间配置了一套完美的开发环境——写了几个 Skills、配了几个 Hooks、接了几个 MCP。现在你的团队里其他人也想要这套配置。

如果没有 Plugin，你需要把每个文件单独发给每个人，告诉他们放在哪里、怎么配置。这很麻烦，而且容易出错。

有了 Plugin，你可以把所有东西打包成一个 Plugin，别人只需要一条命令安装就行了。

Plugin 还支持：
- **版本管理**：Plugin 有版本号，你可以更新、回滚
- **命名空间**：不同 Plugin 之间不会冲突
- **团队复用**：整个团队使用同一套 Plugin
- **分发**：可以分享给社区里的其他人

---

## Slide 43 — 四种扩展机制的对比

让我们把四种扩展机制放在一起对比：

**Skills（技能）**：
- 本质：Reusable Procedures（可复用的流程）
- 作用：教 Agent 怎么做某件事
- 触发方式：模型自动判断 或 用户手动调用
- 类比：一本操作手册

**MCP（外部协议）**：
- 本质：External Reach（外部触达）
- 作用：让 Agent 能连接外部服务
- 触发方式：Agent 在需要时调用
- 类比：一个万能遥控器

**Hooks（钩子）**：
- 本质：Lifecycle Automation（生命周期自动化）
- 作用：在特定事件发生时自动执行操作
- 触发方式：事件驱动，自动触发
- 类比：一个定时器/触发器

**Plugins（插件）**：
- 本质：Packaging & Distribution（打包与分发）
- 作用：把 Skills、Hooks、MCP 等打包在一起
- 触发方式：安装后自动生效
- 类比：一个工具箱/料理包

---

## Slide 45 — 总结

让我们回顾一下今天学到的内容。

**第一部分：Agentic Loop**
- 核心循环：收集上下文 → 生成行动 → 执行工具 → 重复
- 关键原则：Model Proposes, Harness Executes
- 权限系统：Manual / Accept Edits / Bypass / Auto 四种模式
- 上下文管理：Compaction（压缩）和 Demand-Driven Access（按需访问）

**第二部分：Memory**
- 两种记忆：Context（临时的）和 Persistent（持久的）
- 持久记忆的两种机制：CLAUDE.md 和 Auto Memory
- CLAUDE.md 有四个层级：Managed / User / Project / Local
- Auto Memory 有四种类型：user / feedback / project / reference
- 记忆要常更新，过时的记忆比没有记忆更糟

**第三部分：Extending the Agent**
- Skills：教 Agent 怎么做
- MCP：让 Agent 能连接外部服务
- Hooks：在特定时刻自动执行操作
- Plugins：把一切打包分发

理解了这些，你就不再只是一个"用"Agent 的人——你能**控制**它、**调教**它、**扩展**它。这才是真正掌握 AI Agent 的关键。
