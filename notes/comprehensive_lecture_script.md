## 第 4 页：输入提示词后发生了什么

我们先从一个最基本的问题开始：当你给 Agent 输入一个提示词后，到底发生了什么？

这个问题看似简单，但理解它的答案是理解整个 Agent 系统的关键。

先看左边——**传统 LLM 交互**。流程非常简单：用户输入一句话，模型生成一段文字，然后返回结果。这是一个单轮的、无状态的对话。模型本身不能主动执行任何操作——它只能生成文本。就像你跟一个很聪明的人聊天，他只能说话，不能动手做事。

再看右边——**Agent 模式**。这里完全不同。模型可以调用工具。工具执行的结果会反馈给模型，模型根据结果决定下一步行动。这个过程会不断循环，直到任务完成。模型不仅能"想"，还能"做"。

所以我们可以用一个公式来概括：**Agent = LLM + Tools + Loop**。LLM 提供推理能力，Tools 提供行动能力，Loop 把两者串联起来形成自主的工作流程。这三者缺一不可——没有 LLM 就没有智能，没有 Tools 就无法行动，没有 Loop 就只是一次性的交互。

## 第 5 页：智能体循环三步

智能体循环具体包含三个步骤，我们逐一来看。

**第一步是模型推理。** LLM 分析当前的状态——包括用户的请求、之前的对话历史、工具返回的结果等——然后决定下一步该做什么。它可能直接生成文本回答用户，也可能决定调用某个工具。这一步的核心是"决策"——做什么，怎么做。

**第二步是工具调用。** Harness（也就是 Agent 框架，比如 Claude Code、Cursor 等）执行模型选择的工具。这可能是读取文件、运行命令、搜索代码、浏览网页等等。注意，模型本身不执行工具——它只是"说"要调用什么工具、传什么参数，真正的执行由 Harness 完成。

**第三步是结果反馈。** 工具执行的结果会被添加到上下文中，成为模型下一轮推理的输入。然后模型继续推理，决定下一步，如此循环。

这三个步骤不断重复，直到模型认为任务已经完成，生成了最终回答，不再调用工具为止。这个循环看起来简单，但它是一切 Agent 行为的基础。后面讲的所有内容——记忆、工具设计、多 Agent——都是在这个循环的基础上展开的。

## 第 6 页：Agentic Loop 实例

我们来看一个具体的 Agentic Loop 运行实例。假设用户说"帮我修复登录页面的 bug"。

**第一轮循环：**
- **Thought：** 模型分析请求，决定先找到登录页面的代码文件
- **Action：** 调用 `grep("login", glob="**/*.tsx")`
- **Observation：** 返回 3 个匹配文件，其中 `src/pages/Login.tsx` 最相关

**第二轮循环：**
- **Thought：** 找到文件了，需要读取内容来分析 bug
- **Action：** 调用 `read_file("src/pages/Login.tsx")`
- **Observation：** 发现第 42 行有一个空指针引用——`user.profile.name` 没有检查 `user` 是否为 null

**第三轮循环：**
- **Thought：** 找到 bug 了，需要添加空值检查
- **Action：** 调用 `edit("src/pages/Login.tsx", old="user.profile.name", new="user?.profile?.name")`
- **Observation：** 修改成功

**第四轮循环：**
- **Thought：** 修复完成，应该运行测试确认没有引入新问题
- **Action：** 调用 `bash("npm test -- -t 'login'")`
- **Observation：** 所有测试通过

**第五轮：** 模型认为任务完成，生成最终回答给用户。不再调用工具，循环终止。

这个例子展示了 Agentic Loop 的核心：每一步都基于上一步的结果来做决策。模型不是一开始就知道所有答案，而是通过与环境交互逐步解决问题。

## 第 7 页：输入前的六层上下文

在模型开始推理之前，它看到的并不是简单的"你的问题"。实际上，模型看到的是六层信息的完整组合。理解这六层结构非常重要，因为它告诉我们：模型的行为不仅仅取决于你说了什么，还取决于整个上下文的组合。

从底层到顶层依次是：

**第一层是模型权重**，也就是预训练知识。这是模型在训练阶段学到的所有知识——语言理解、编程能力、世界知识等等。这是它能力的基础，也是最大的"记忆"。对于 Claude 来说，这些权重是固定的，我们通常无法修改。

**第二层是记忆文件**，比如 CLAUDE.md。这些文件包含了项目的约定、用户的偏好等持久化信息。它们每次会话开始时被加载到上下文中。

**第三层是工具定义**，也就是模型可以调用的所有工具的列表和描述。模型需要知道有哪些工具可用，以及每个工具的参数和用途。工具定义通常占几百到几千 tokens。

**第四层是系统提示词**，定义了模型的行为规则——比如"你是一个编程助手"、"不要执行危险命令"等。系统提示词通常由 Harness 生成，用户不直接看到。

**第五层是对话历史**，之前所有轮次的消息和工具调用结果。这是增长最快的层——每次工具调用都会增加大量内容。

**第六层是用户输入**，也就是当前这一轮的提示词。

这六层从下到上，从固定到动态，从底层到表层。模型在推理时会综合考虑所有层的信息。

## 第 8 页：上下文增长与压缩

这六层信息加起来，就构成了模型的上下文窗口。但上下文窗口是有限的——比如 Claude 是 200K tokens。

问题在于，每次工具调用都会增加上下文的内容。读一个文件可能消耗几千 tokens，运行一个命令可能返回几百 tokens 的输出。长对话下来，上下文很快就会接近限制。

左边列出了三个问题：每次工具调用都增加上下文、长对话会超出窗口限制、早期信息可能被截断。

右边的解决方案是自动压缩。当上下文接近限制时（比如达到 90%），系统会自动触发压缩。压缩的过程是让 LLM 总结早期的对话内容，保留关键信息，丢弃细节。用户也可以手动触发压缩，比如使用 `/compact` 命令。

## 第 9 页：工具和记忆赋予智能体能力

让 Agent 真正强大的有两个东西：工具和记忆。这两者的区别很重要。

**工具赋予 Agent 短期能力。** 读文件、写文件、运行命令、搜索代码、浏览网页——这些工具让 Agent 能够行动。每次会话中，Agent 都可以使用这些工具来完成任务。工具是"即插即用"的——定义好了就能用，不需要学习。

**记忆赋予 Agent 长期知识。** 项目约定、用户偏好、过去的决策和经验——这些记忆让 Agent 能够学习。记忆是跨会话持久化的，所以 Agent 不需要每次都从头开始。

打个比方：工具就像你的手和脚，让你能做事；记忆就像你的大脑，让你积累经验。一个只有工具没有记忆的 Agent，就像一个每天失忆的人——他有能力做事，但每次都要重新学习怎么做。没有记忆的 Agent，每次对话都要重新了解项目结构、代码风格、用户偏好。有了记忆，Agent 可以持续积累知识，变得越来越了解你的项目和你这个人。

## 第 10 页：智能体记忆的层次

记忆系统有不同的层次，从简单到复杂，从临时到持久。

**最底层是上下文窗口。** 这是当前对话的内容，会话内自动管理，会话结束就消失了。它是最临时的记忆形式，但也是模型直接"看到"的记忆。容量有限，需要精心管理。

**往上是 CLAUDE.md。** 这是项目级的记忆文件，跨会话持久化。你可以手动维护它，Agent 也可以在会话中自动追加和修改。它放在项目根目录，每次会话开始时自动加载。

**再往上是用户级记忆。** 这是跨项目的个人偏好，比如"用中文回复"、"保持简洁"。这些偏好对所有项目都生效，存储在用户级别的配置中。

**最顶层是专用记忆系统。** 比如 Mem0、Graphiti 等，通过 API 驱动，支持智能检索。这些系统可以处理大量的记忆，并提供语义搜索等高级功能。它们通常是独立的服务，可以跨多个 Agent 和会话共享记忆。

这四个层次从简单到复杂，从轻量到重量。对于大多数项目，CLAUDE.md 就够用了；当记忆需求变复杂时，才需要考虑专用记忆系统。

## 第 11 页：记忆类型详解

记忆系统可以分为三种类型，类比人类的记忆方式：

**情景记忆（Episodic Memory）：** 记录具体的事件和经历。比如"2024年3月15日，用户报告了登录页面的 bug，根因是 auth.ts 第 42 行的空指针"。这就像你记得上周三发生了什么。情景记忆帮助 Agent 回忆过去的具体交互，避免重复犯错。

**语义记忆（Semantic Memory）：** 存储通用的事实和知识。比如"这个项目使用 TypeScript + React"、"用户偏好中文回复"。这就像你知道"北京是中国的首都"这样的知识。语义记忆是 CLAUDE.md 的主要内容。

**程序记忆（Procedural Memory）：** 记住如何做事的方法和流程。比如"修复 bug 的标准流程：先复现、再定位、然后修复、最后测试"。这就像你会骑自行车——你知道怎么做，但不一定能用语言描述。程序记忆体现在 Skill 和 Instructions 中。

三种记忆类型各有用途：情景记忆帮助避免重复错误，语义记忆提供项目知识，程序记忆标准化工作流程。好的记忆系统应该同时支持这三种类型。

## 第 12 页：CLAUDE.md 应该包含什么

CLAUDE.md 是最常用的记忆形式。它应该包含什么内容呢？主要有四个方面：

**构建与测试命令。** 告诉 Agent 如何构建项目、如何运行测试、如何启动开发服务器、常用的 npm 或 pip 命令是什么。这样 Agent 就不需要每次都问用户。比如"运行测试用 `npm test`，单个测试用 `npm test -- -t 'name'`"。

**代码风格约定。** 命名规范、文件组织方式、注释要求、错误处理风格。这些约定确保 Agent 生成的代码符合项目标准。比如"TypeScript strict mode"、"错误消息用小写开头不加句号"。

**项目架构。** 关键目录的用途、模块间的依赖关系、数据流向。这些信息帮助 Agent 理解项目的整体结构，知道改一个地方会影响哪些其他地方。

**常见陷阱。** 记录那些容易踩的坑——比如"不要做 X，因为会导致 Y"、"Z 函数有特殊的调用顺序"、"W 配置需要特定的环境变量"。这些经验教训是最有价值的记忆，因为它们往往是 Agent 自己很难从代码中推断出来的。

## 第 13 页：CLAUDE.md 实例

我们来看一个具体的 CLAUDE.md 实例。

左边是一个完整的 CLAUDE.md 文件，右边是对它的解读。

这个文件分为四个部分：

**Build & Test Commands** 部分列出了构建、测试、lint 的具体命令。比如 `npm run build`、`npm test`、`npm test -- -t "name"`（运行单个测试）、`npm run lint -- --fix`（自动修复 lint 问题）。注意这些命令都非常具体——Agent 可以直接复制粘贴运行，不需要猜测。

**Code Style** 部分规定了代码风格：TypeScript strict mode、优先使用函数式组件（React 项目）、用 Zod 做运行时验证、错误消息用 sentence case（首字母大写，不加句号）。这些规则看起来很细，但正是这些细节决定了代码的一致性。

**Memory Rules** 部分定义了记忆的规则：修复 bug 后要记录根因到 `docs/decisions.md`、不要重复之前失败的修复方案、调试前先查看决策文档。这些规则让 Agent 能够从过去的经验中学习，避免重复犯错。

**User Preferences** 部分记录用户偏好：用中文回复、解释不超过三句话、提交前一定要运行测试。这些是用户的个人习惯。

CLAUDE.md 的关键设计原则是：纯文本（可 diff、可 git 追踪）、结构化（用 Markdown 标题分区）、可操作（写具体的命令和规则，不写空泛的描述）、可演化（Agent 和用户共同维护）。

## 第 14 页：CLAUDE.md 实战对比

我们来看两个 CLAUDE.md 的对比，理解什么是好的写法。

**错误示范：**
- "写好代码" — 太模糊，模型不知道"好"的标准是什么
- "注意性能" — 没有具体指标，模型无法判断
- "遵循最佳实践" — 什么是最佳实践？每个项目不同
- "项目结构要合理" — 没有说明什么样的结构是合理的

这些写法的问题在于：它们看起来有道理，但模型无法据此做出具体的决策。

**正确示范：**
- "TypeScript strict mode，不允许 any 类型" — 明确的规则，模型可以检查
- "API 响应时间 < 200ms，使用 Lighthouse 测量" — 可衡量的指标
- "组件放在 src/components/，每个组件一个文件夹，包含 index.tsx 和 styles.module.css" — 具体的结构说明
- "不要使用 moment.js，已迁移到 dayjs，API 参考 dayjs 文档" — 具体的约束和替代方案

关键区别：好的 CLAUDE.md 是**可操作的**——模型读到后能立即知道该做什么、不该做什么。坏的 CLAUDE.md 是**描述性的**——看起来有道理但无法指导行动。

## 第 15 页：四种扩展机制

除了记忆，我们还可以通过四种机制来扩展 Agent 的能力。这四种机制从轻量到重量，从简单到复杂。

**Skills（技能）** 是可复用的工作流程，定义在 skill.md 文件中。每个 Skill 包含工具列表、执行步骤和约束条件。比如"代码审查"就是一个 Skill——它定义了审查的步骤、使用的工具、输出的格式。Skill 是最轻量的扩展方式。

**MCP（模型上下文协议）** 是连接外部工具的标准接口。通过 MCP，Agent 可以调用数据库、文件系统、API 等外部服务。MCP 类似于 USB-C——一个统一的接口，连接各种不同的设备。

**Hooks（钩子）** 是生命周期自动化脚本。它们在特定事件发生时自动执行，无需 Agent 主动调用。比如"每次文件修改后自动格式化代码"就是一个 Hook。Hooks 的特点是"被动触发"——不需要 Agent 记得去做，系统会自动执行。

**Plugins（插件）** 是打包分发层。一个 Plugin 可以包含多个 Skills、MCP 配置、Hooks 和 CLAUDE.md 片段，作为一个整体来安装和分享。Plugin 是最重量级的扩展方式，但也是最完整的。

这四种机制让 Agent 从"通用助手"变成"领域专家"。你可以根据需要组合使用它们。

## 第 16 页：技能结构

我们来看看 Skill 的具体结构。一个 skill.md 文件包含四个部分：

**Description** 描述这个技能的用途，以及何时应该触发它。比如"Review pull requests for bugs, style, and security issues"。Description 非常重要——Agent 根据它来判断什么时候应该加载这个 Skill。

**Tools** 列出这个技能允许使用的工具。比如 code-reviewer 只需要 `read_file`、`list_dir` 和 `search`，不需要 `write_file`。这里体现了最小权限原则——只给 Skill 它需要的工具，不多给。

**Instructions** 是详细的执行步骤。比如审查 PR 时：先仔细阅读 diff，然后检查 OWASP Top 10 问题，验证错误处理，检查测试覆盖率，最后按 🔴🟡🟢 分级输出。Instructions 越具体越好——模糊的指令会导致不稳定的输出。

**Constraints** 定义限制和边界。比如"不要直接修改代码"、"始终引用 file:line"、"每次审查最多 10 个问题"。Constraints 告诉 Skill 什么不能做，和 Instructions 告诉它什么要做同样重要。

Skill 的加载方式有两种：用户显式调用（如 `/code-reviewer`），或者 Agent 根据上下文自动选择。Skill 只在需要时加载，这样可以节省上下文空间——这是一个重要的设计决策。

这是一个完整的 code-reviewer skill.md 实例。左边是代码，右边是解读。

## 第 19 页：MCP 作为外部能力层

MCP（Model Context Protocol，模型上下文协议）是 Agent 连接外部工具的标准接口。你可以把它类比为 USB-C 之于硬件设备——一个统一的接口，连接各种不同的外部服务。

在 MCP 之前，每个 Agent 框架都有自己的方式来连接外部工具——有的用 REST API，有的用 SDK，有的用命令行。这导致了严重的碎片化——一个工具要支持多个 Agent 框架，就得写多个适配器。MCP 的出现解决了这个问题：所有 Agent 都用同一个协议来连接工具，工具提供商只需要写一个 MCP Server。

MCP 提供三个核心抽象：

**Tools（工具）** 是 Agent 可调用的函数。比如查询数据库、发送 HTTP 请求、操作文件系统等。Tools 是有副作用的——它们会改变状态。

**Resources（资源）** 是 Agent 可读取的数据。比如数据库中的表、文件系统中的文件、API 返回的数据等。Resources 是只读的——它们不改变状态。

**Prompts（提示模板）** 是预定义的提示词模板，帮助 Agent 更好地与外部服务交互。比如一个数据库 MCP Server 可能提供"分析查询性能"的提示模板。

左边展示了两个代码示例。上面是 MCP Server 的配置（mcp.json），定义了两个服务器：database（PostgreSQL）和 filesystem（文件系统）。下面是 MCP Tool 的 TypeScript 定义，定义了一个 `query_users` 工具，接受 name 和 limit 参数，执行 SQL 查询并返回结果。

通过 MCP，Agent 可以调用数据库、文件系统、API 等各种外部服务，极大地扩展了它的能力边界。

## 第 21 页：钩子作为生命周期自动化

Hooks 是在特定事件发生时自动执行的脚本，类似于 Git Hooks 的概念。如果你用过 Git，你就知道 `pre-commit` hook 可以在提交前自动运行 lint 检查，`pre-push` hook 可以在推送前运行测试。Hooks 在 Agent 系统中的角色是一样的。

与 Skills 和 MCP 不同，Hooks 不需要 Agent 主动调用。它们由 Harness 在后台自动触发。Agent 甚至可能不知道 Hooks 的存在——它只需要正常调用工具，Hooks 会在背后默默执行。

左边列出了常见的 Hook 事件：

- `pre-tool-call`：在工具调用之前执行，可以用于参数验证或权限检查。比如检查文件路径是否在允许的范围内。
- `post-tool-call`：在工具调用之后执行，可以用于结果处理或日志记录。比如自动格式化修改过的文件。
- `session-start`：会话开始时执行，可以用于加载项目上下文。比如自动读取项目的 README 和 CLAUDE.md。
- `session-end`：会话结束时执行，可以用于保存状态或清理资源。比如自动提交未保存的更改。

右边的代码示例展示了一个 `post-tool-call` Hook：每次文件修改后自动运行 Prettier 格式化。这样就不需要 Agent 每次都记得运行格式化命令了。Hook 检查工具名称是否是 `write_file` 或 `edit`，如果是，就对修改的文件运行 `npx prettier --write`。

Hooks 的价值在于：把重复性的、容易忘记的操作自动化。Agent 不需要"记得"做这些事，Hooks 会自动处理。


---

## 第 22 页：Hook 生命周期详解

让我们深入理解 Hook 的完整生命周期。

**Pre-Tool-Call 阶段（工具调用前）：**
- 触发时机：Agent 决定调用工具，但工具还没执行
- 可以做什么：参数验证（检查文件路径是否在允许范围内）、权限检查（确认 Agent 有权执行该操作）、日志记录
- 可以阻止吗：可以！如果验证失败，Hook 可以阻止工具调用执行

**Post-Tool-Call 阶段（工具调用后）：**
- 触发时机：工具执行完毕，结果返回给 Agent 之前
- 可以做什么：结果处理（自动格式化修改的文件）、日志记录、通知（发送消息通知团队）
- 可以修改结果吗：可以！比如自动格式化代码后再返回

**Session-Start 和 Session-End：**
- Session-Start：加载项目上下文、初始化环境变量、恢复上次会话状态
- Session-End：保存会话状态、清理临时文件、提交未保存的更改

Hook 的核心价值：**把重复性操作从 Agent 的"待办事项"中移除，交给系统自动处理**。Agent 不需要"记得"运行格式化命令，Hook 会自动做。

## 第 23 页：插件作为打包层

Plugin 是最高层的抽象，它是一个打包分发层。

一个 Plugin 可以包含：多个 Skills（技能定义）、MCP Server 配置、Hooks（自动化脚本）、CLAUDE.md 片段（记忆模板）。

为什么要用 Plugin？四个原因：

**一键安装：** 安装一个 Plugin 就获得了完整的领域能力，不需要逐个配置。比如安装一个"React 开发"Plugin，你就自动获得了代码审查、组件生成、测试编写等所有能力。

**可分享：** 团队或社区可以共享 Plugin，让每个人都能快速获得相同的能力。比如你的团队可以开发一个内部 Plugin，包含所有项目的约定和工具。

**版本管理：** Plugin 有明确的版本，可以管理依赖和兼容性。比如 v2.0 的 Plugin 可能需要新版的 MCP Server。

**隔离：** 不同项目可以使用不同的 Plugin，互不干扰。比如前端项目用前端 Plugin，后端项目用后端 Plugin。

公式：**Plugin = Skills + MCP + Hooks + Memory Templates**。Plugin 本身不做任何具体的事情——它只是把其他四种机制打包在一起，方便分发和管理。

## 第 24 页：案例研究：Superpowers

Superpowers 是一个很好的案例，展示了如何通过 Skills 让同一个模型表现出不同的专业能力。

Superpowers 使用相同的 Claude 模型，但通过 9 个不同的 Skills 定义了 9 种专业工作流。每个 Skill 有专门的工具和指令：

- `code-reviewer`：代码审查——只读工具，检查 bug 和安全问题
- `test-writer`：测试生成——读写工具，分析代码并生成测试
- `doc-generator`：文档生成——读写工具，分析代码并生成文档
- `refactorer`：代码重构——读写工具，优化代码结构
- `debugger`：调试助手——读和执行工具，分析错误并定位问题
- 等等

关键洞察是：**模型能力不变，通过 Skill 改变工作方式**。同一个模型，加载不同的 Skill，就能扮演不同的专业角色。这就像一个人——他有基础能力，但穿上不同的"工装"（Skill），就能做不同的专业工作。

这个案例很好地说明了 Skill 的价值：你不需要换模型，只需要换 Skill 就能改变 Agent 的行为模式。

## 第 25 页：Superpowers 架构

Superpowers 的架构流程是：用户请求 → Skill Router → Selected Skill → 执行结果。

有三个关键组件：

**Session-Start 脚本：** 会话开始时自动加载项目上下文和可用 Skills 列表。这样用户不需要每次都重复说明项目信息。Session-Start 是一个 `session-start` Hook，它在会话开始时自动运行，读取项目的 CLAUDE.md、扫描可用的 Skills、设置初始上下文。

**Skill 选择：** 根据用户意图或显式调用（`/skill-name`）加载对应的 Skill。Agent 可以自动判断需要哪个 Skill（比如用户说"帮我审查这个 PR"，Agent 自动加载 code-reviewer），用户也可以手动指定。Skill Router 的核心是一个匹配逻辑——根据用户请求和 Skill 的 Description 来决定加载哪个 Skill。

**上下文隔离：** 每个 Skill 只加载需要的工具和指令，避免上下文污染。比如 code-reviewer 只需要读和搜索的工具，不需要写的工具。上下文隔离非常重要——如果把所有工具和指令都加载到上下文中，不仅浪费空间，还可能干扰模型的决策。

## 第 26 页：Superpowers 的设计经验

从 Superpowers 项目中，我们可以总结出五条设计经验。这些经验不仅适用于 Superpowers，也适用于任何使用 Skill 的系统。

**第一，Skill 要具体。** 不要写"写好代码"这样模糊的指令，要写"检查 SQL 注入、XSS、硬编码密钥"这样具体的检查项。模糊的指令会导致不稳定的输出——模型可能每次理解都不一样。

**第二，限制工具集。** code-reviewer 不需要 `write_file`，只给 `read` 和 `search`。最小权限原则同样适用于工具——给得越多，出错的风险越大。

**第三，明确输出格式。** 用 🔴🟡🟢 分级，强制 file:line 引用。这样输出是结构化的、可操作的。如果没有明确格式，模型可能每次输出的格式都不一样。

**第四，设置边界。** 明确告诉 Skill 什么不能做，比如"不要直接修改代码"。边界和指令同样重要——有时候告诉模型"不做什么"比告诉它"做什么"更有效。

**第五，Session-Start 很重要。** 自动加载上下文可以大大减少用户重复说明的成本。一个好的 Session-Start 脚本能让用户感觉"Agent 已经了解我的项目了"。

## 第 27 页：Caveman 案例研究

Caveman 解决的是一个不同的问题：上下文爆炸。

在长对话中，上下文会消耗大量 tokens，导致四个问题：

- **API 成本高昂：** tokens 是按量计费的，上下文越长，每次 API 调用的成本越高
- **模型性能下降：** 上下文越长，模型的推理速度越慢（attention 的计算复杂度是 O(n²)）
- **用户等待时间长：** 推理慢意味着响应慢，用户体验差
- **上下文窗口被快速填满：** 填满后就需要压缩，压缩会丢失信息

Caveman 的解决方案是**双向压缩**：输入和输出都压缩。它用 Plugin 打包压缩逻辑，通过 Response Skill 让输出更简洁，同时自动摘要早期对话。

核心思想是：**压缩 Agent 的 tokens，而不是压缩模型的能力**。我们减少的是信息的冗余，而不是信息的质量。就像压缩文件——文件变小了，但内容没有丢失。

---

## 第 28 页：Caveman 双向压缩

双向压缩具体怎么做？

**输入压缩：** 自动摘要早期对话，只保留关键决策和结果，丢弃中间推理过程。这类似于 `/compact` 功能，但更智能——它知道什么该保留、什么该丢弃。比如"用户要求修复登录 bug"这个信息要保留，但中间"先读了 auth.ts，发现第 42 行有问题"这样的过程可以丢弃。

**输出压缩：** 通过 Response Skill 约束输出格式。比如"用 3 句话回答"、"不要解释基础概念"、"直接给代码，不要注释"。这些约束让模型的输出更简洁，减少输出 tokens。

效果非常显著：从 45K tokens 压缩到 12K tokens，减少了 73%。成本从 $0.45 降到 $0.12，延迟从 8 秒降到 2.5 秒。这些数字说明上下文管理不仅是技术问题，也是经济问题——更少的 tokens 意味着更低的成本和更好的用户体验。

## 第 30 页：ReAct Loop 回顾

ReAct Loop 是 Agent 循环的经典模式。ReAct = Reasoning + Acting，让模型边想边做。这个模式来自 2022 年 Yao et al. 的论文，是 Agent 系统的理论基础之一。

循环包含三个步骤：

**Thought（思考）：** 模型分析当前状态，推理下一步该做什么。这是推理阶段。模型会"想"：我现在知道什么？我还缺什么信息？我应该调用哪个工具？

**Action（行动）：** 模型调用工具执行操作——读文件、搜索、运行命令等。这是行动阶段。模型把思考的结果转化为具体的操作。

**Observation（观察）：** 工具返回结果，成为下一轮思考的输入。这是观察阶段。模型"看到"行动的结果，然后继续思考。

这三个步骤不断循环，直到任务完成。ReAct 的核心价值在于：它让模型不仅仅是生成文本，而是能够通过与环境的交互来解决问题。传统的 LLM 只能"说"，ReAct 让 LLM 能"做"。


---

## 第 31 页：ReAct Loop 完整实例

让我们看一个完整的 ReAct Loop 调试实例。用户报告"API 返回 500 错误"。

**Thought 1：** 用户报告 API 500 错误。我需要先找到相关的 API 路由代码。
**Action 1：** `grep("api/users", glob="**/*.ts")`
**Observation 1：** 找到 `src/routes/users.ts`

**Thought 2：** 找到了路由文件，需要查看具体实现来定位错误原因。
**Action 2：** `read_file("src/routes/users.ts")`
**Observation 2：** 发现第 28 行调用了 `db.query()`，但没有 try-catch 包裹

**Thought 3：** 可能是数据库查询抛出了异常。需要检查数据库连接。
**Action 3：** `bash("curl -s http://localhost:3000/api/users")`
**Observation 3：** 返回 "Error: connection refused"——数据库没有运行

**Thought 4：** 找到根因了！数据库连接失败。需要检查数据库服务状态。
**Action 4：** `bash("docker ps | grep postgres")`
**Observation 4：** 没有输出——PostgreSQL 容器没有运行

**Thought 5：** 需要启动数据库容器。
**Action 5：** `bash("docker start postgres")`
**Observation 5：** 容器启动成功

**Thought 6：** 数据库启动了，验证 API 是否恢复正常。
**Action 6：** `bash("curl -s http://localhost:3000/api/users | head -1")`
**Observation 6：** 返回正常 JSON 数据

**最终回答：** 问题已修复。根因是 PostgreSQL 数据库容器未运行。已启动容器，API 恢复正常。

这个例子展示了 ReAct 的核心：每一步 Thought 都基于前一步的 Observation，逐步缩小问题范围。

## 第 32 页：Agent Loop 示意图

这张图展示了完整的 Agent Loop 流程：用户输入 → LLM 推理 → 工具调用 → 结果反馈 → 循环直到任务完成。

循环的终止条件有四种：

1. **模型生成最终回答（不再调用工具）：** 这是正常的终止方式。模型认为任务完成了，直接生成回答给用户。
2. **达到最大迭代次数（防止无限循环）：** 这是一个安全机制。如果模型陷入了循环——比如反复读同一个文件——最大迭代次数会强制终止。
3. **用户中断：** 用户可以随时按 Ctrl+C 或点击停止按钮来中断循环。
4. **发生错误：** 工具调用失败、API 超时等错误也可能终止循环。

关键组件有三个：

**Harness（框架）：** 管理整个循环的执行，包括上下文管理、工具调度、错误处理等。Harness 是 Agent 系统的"操作系统"。

**Tool Executor（工具执行器）：** 负责执行具体的工具调用。它接收模型的指令，执行操作，返回结果。

**Context Manager（上下文管理器）：** 管理上下文窗口，决定什么信息进入、什么信息退出。这是 Agent 系统中最复杂的组件之一。

## 第 33 页：编码 Agent 的核心组件

一个编码 Agent 需要哪些工具？我们按功能分类：

**搜索工具：** `grep`（文本搜索）、`find`（文件查找）、`glob`（模式匹配）、语义搜索（向量搜索）。这些工具帮助 Agent 在代码库中找到相关信息。搜索是编码 Agent 最常用的操作——在修改代码之前，你得先找到要修改的代码。

**读取工具：** `read_file`（读取文件）、`list_dir`（列出目录）、`head/tail`（查看文件的部分内容）。这些工具让 Agent 能够读取代码。读取是安全的操作——它不会改变任何状态。

**编辑工具：** `write_file`（写入文件）、`edit`（精确替换）、`insert`（插入内容）。这些工具让 Agent 能够修改代码。编辑是有副作用的操作——它们会改变文件系统状态。

**执行工具：** `bash`（运行 Shell 命令），支持后台运行和超时控制。这是最强大的工具——它可以做任何事情，也是最危险的工具。

**其他工具：** `browser`（网页浏览）、`web_fetch`（获取网页内容）、MCP 工具（数据库、API 等）。这些工具扩展了 Agent 的能力边界。

## 第 34 页：编码任务流程实例

让我们看一个编码 Agent 处理完整任务的流程。用户说"给项目添加用户认证功能"。

**阶段 1：搜索和理解**
- Agent 先用 `glob("src/**/*.ts")` 了解项目结构
- 用 `grep("auth|login|session")` 搜索现有认证代码
- 用 `read_file("package.json")` 查看已安装的依赖

**阶段 2：规划和设计**
- 根据搜索结果，确定使用 JWT + bcrypt 方案
- 规划需要创建的文件：`src/auth/login.ts`、`src/auth/register.ts`、`src/middleware/auth.ts`

**阶段 3：实现代码**
- 用 `write_file` 创建认证模块
- 用 `edit` 修改 `src/app.ts` 添加路由
- 每写完一个文件就运行 `bash("npm run lint")` 检查代码质量

**阶段 4：测试验证**
- 用 `write_file` 创建测试文件
- 用 `bash("npm test")` 运行所有测试
- 测试失败后用 `read_file` 查看错误，用 `edit` 修复

**阶段 5：提交结果**
- 用 `bash("git add && git commit")` 提交代码
- 生成总结报告给用户

这个流程展示了编码 Agent 如何组合使用搜索、读取、编辑、执行四类工具来完成一个完整任务。

## 第 35 页：搜索方法对比

不同的搜索方法适用于不同的场景：

**grep** 适合精确文本匹配。优点是快速、准确；缺点是需要知道关键词。比如你知道函数名叫 `calculateTotal`，用 grep 一搜就能找到。但如果你只知道"有一个计算总价的函数"，grep 就帮不上忙了。

**glob** 适合文件名模式匹配。优点是能快速找到相关文件；缺点是只能匹配文件名，不能搜索文件内容。比如 `**/*.tsx` 可以找到所有 React 组件文件。

**find** 适合复杂的文件查找。优点是支持灵活的条件组合（按名称、大小、修改时间等）；缺点是语法比较复杂。比如"找到最近 7 天修改过的、大于 100KB 的 TypeScript 文件"。

**语义搜索** 适合概念查找。优点是能理解意图，即使关键词不完全匹配也能找到相关内容；缺点是需要预先建立向量索引。比如搜索"用户认证"可以找到 `login.ts`、`auth.middleware.ts` 等文件，即使这些文件名里没有"认证"这个词。

最佳实践是：**先用 glob 定位文件，再用 grep 查找内容**。这样既高效又准确。

## 第 36 页：编辑方法对比

编辑文件有两种主要方法：

**write_file（全量写入）：** 覆盖整个文件。适合创建新文件或完全重写。但很危险——如果忘记包含某些内容，那些内容就会丢失。想象一下你有一个 500 行的文件，你用 write_file 重写了前 100 行，但忘记包含后 400 行——那 400 行就永远丢失了。

**edit（精确替换）：** 指定 old_string 和 new_string，只修改匹配的部分。更安全，不会意外删除其他内容。这是大多数修改场景的推荐方法。

举个例子：要把 `return a - b` 改成 `return a + b`，用 edit 工具只需要指定这两个字符串，其他代码完全不受影响。即使文件有几千行，edit 也只会修改这一处。

edit 工具的一个关键细节是：old_string 必须在文件中唯一匹配。如果有多个匹配，edit 会拒绝执行，要求你提供更多的上下文来消除歧义。这是一个安全机制——它防止了"改错了地方"的问题。

## 第 37 页：Shell 工具执行

Shell 工具有两种执行模式：

**前台执行：** 等待命令完成，返回输出。比如 `bash("npm test")` 会等待所有测试运行完毕，然后返回测试结果。适合快速命令——几秒钟内能完成的。

**后台执行：** 立即返回，稍后检查结果。比如 `bash("npm run dev", run_in_background=true)` 会立即返回，然后你可以用 `bash("curl http://localhost:3000")` 来验证服务是否启动成功。适合长时间运行的命令——比如开发服务器、数据库等。

安全方面需要考虑三点：

- **权限检查：** 哪些命令允许执行？比如 `rm -rf /` 应该被禁止，但 `npm test` 应该被允许。
- **沙箱隔离：** 限制文件系统访问。比如 Agent 只能访问项目目录，不能访问系统文件。
- **资源限制：** CPU、内存、时间。比如限制命令最多运行 5 分钟，最多使用 2GB 内存。

Shell 工具是最强大的工具，也是最危险的工具。一个好的 Agent 系统必须在能力和安全之间找到平衡。

## 第 38 页：工具设计最佳实践

好的工具设计有六个原则：

**原子性：** 每个工具做一件事，做好它。不要一个工具既读文件又写文件又运行命令。原子工具更容易理解、测试和组合。

**明确的输入输出：** 参数类型清晰，返回值可预测。Agent 应该能准确知道调用这个工具会得到什么。比如 `read_file(path)` 应该返回文件内容，而不是有时候返回内容有时候返回错误码。

**错误处理：** 失败时返回有用的错误信息，而不是崩溃。错误信息应该帮助 Agent 理解问题并尝试修复。比如"文件不存在：/path/to/file"比"Error: ENOENT"更有用。

**幂等性：** 相同的输入产生相同的结果（尽可能）。这样重试是安全的。比如 `write_file` 是幂等的——写两次和写一次的效果一样。但 `bash("npm test")` 不完全是幂等的——测试可能因为随机因素而不同。

**最小权限：** 只给工具必要的访问权限。比如 code-reviewer 不需要写文件的权限。

**可组合：** 工具之间可以组合使用，解决复杂问题。比如先用 glob 找文件，再用 grep 搜内容，最后用 edit 修改。

好的工具设计等于 Agent 成功的一半。如果工具设计不好，再强的模型也难以发挥。

## 第 39 页：从提示词工程到上下文工程

随着 Agent 系统的发展，我们的关注点从"提示词工程"转向了"上下文工程"。这是一个重要的范式转变。

**提示词工程**关注单次输入：优化措辞和格式，假设上下文是固定的。它适合单轮对话场景。比如"你是一个专业的代码审查员，请审查以下代码"——这是一个提示词，它优化的是单次输入。

**上下文工程**关注整个上下文窗口：管理信息的进入和退出，动态调整上下文内容。它适合多轮 Agent 循环场景。比如"在这个 50 轮对话中，什么时候加载 Skill、什么时候压缩历史、什么时候丢弃工具结果"——这是上下文工程。

Agent 系统的核心挑战是：**在有限的上下文窗口中放入最相关的信息**。这不是优化一句话的问题，而是管理整个信息流的问题。就像图书馆管理——不是写一本好书的问题，而是在有限的书架上放最有价值的书的问题。

---

## 第 40 页：上下文是有限资源

上下文窗口虽然看起来很大，但实际上是有限资源：

- Claude: 200K tokens
- GPT-4: 128K tokens

看似很大，但很快用完。一个长代码文件可能就是几千 tokens，几次工具调用下来就消耗了很多。一次 `read_file` 可能消耗 3-5K tokens，一次 `bash` 输出可能消耗 1-2K tokens。10 轮对话下来，就可能消耗 50-100K tokens。

性能影响也很显著：上下文越长，推理越慢（attention 的计算复杂度是 O(n²)）；成本随 tokens 线性增长；过长的上下文会降低准确性（"Lost in the Middle" 问题——模型容易忽略中间位置的信息，更关注开头和结尾）。

上下文使用策略有四条：
- **准入：** 只让相关信息进入——守护入口
- **卸载：** 按需加载，用完即弃——减少占用
- **转换：** 压缩历史，保留要点——提高效率
- **压缩：** LLM 总结作为最后手段——应急方案

## 第 41 页：上下文管理实例

让我们通过一个具体例子来理解上下文管理的正确和错误做法。

**错误做法：** Agent 接到"重构 auth 模块"的任务后，一次性读取了所有相关文件：auth.ts、users.ts、database.ts、api.ts、config.ts、tests/... 总共 180K tokens。然后开始逐个分析。问题是：大量不相关的代码占据了上下文空间，模型在 180K tokens 中很难找到真正需要修改的部分。结果：响应变慢、准确性下降，"Lost in the Middle" 效应严重。

**正确做法：** Agent 先用 `grep("auth", glob="src/**/*.ts")` 定位相关文件，只读取 auth.ts 和 users.ts（共 15K tokens）。分析完后，需要查看 database.ts 的接口定义，只读取相关的 50 行（3K tokens）。用完 auth.ts 的内容后，将其从上下文中卸载，只保留分析结论。整个过程中上下文占用保持在 45K tokens 左右，快速、准确，还留有余量。

关键区别：好的上下文管理就像一个好的图书管理员——不是把所有书都堆在桌上，而是每次只拿出需要的书，看完放回去，再拿下一本。

## 第 42 页：上下文窗口的解剖

上下文窗口由五层组成，每一层都在争夺有限的空间：

**系统提示词（2-4K tokens）：** 行为规则、工具定义。这是最优先的层，通常不会被压缩。没有系统提示词，模型就不知道自己是 Agent，也不知道有哪些工具可用。

**记忆文件（1-3K tokens）：** CLAUDE.md、项目知识。这些是跨会话的持久化信息。它们占用空间不大，但价值很高。

**对话历史（变化）：** 之前的消息和工具调用结果。这是增长最快的层——每次工具调用都会增加内容。也是最需要管理的层。

**当前输入（变化）：** 用户的最新请求。这是触发推理的输入，必须完整保留。

**预留空间：** 模型生成输出需要的空间。如果上下文填满了，模型就没有空间生成回答了。

每一层都在争夺有限的空间，优先级管理至关重要。好的上下文管理就是在这五层之间找到平衡。

---

## 第 43 页：管理上下文窗口的四种策略

管理上下文窗口有四种策略，从低成本到高成本排列：

**1. 准入（Admission）：** 守护入口，只让相关信息进入上下文。按需加载文件，不要一次性读取全部；使用搜索而非全量扫描。比如不要 `read_file` 一个 1000 行的文件来找一个函数——先用 `grep` 找到函数位置，再 `read_file` 那几行。准入是最低成本的策略——它只是决定什么该进来。

**2. 卸载（Offloading）：** 按需加载，用到时才放入上下文。Skill 只在需要时加载；工具结果用完后可以丢弃。比如 code-reviewer 的 Skill 定义只在审查 PR 时加载，平时不占用上下文空间。

**3. 转换（Transformation）：** 选择性丢弃，压缩历史，保留要点。自动摘要早期对话；保留决策，丢弃推理过程。比如"用户要求修复登录 bug"保留，"先读了 auth.ts 第 42 行"丢弃。

**4. 压缩（Compression）：** LLM 总结，最后的手段。用 LLM 总结长对话，成本高但在必要时有效。压缩本身需要调用 LLM，有成本和延迟。

这四种策略应该优先使用前三种——它们成本更低、信息损失更小。压缩是最后的手段。

## 第 44 页：Agent = Model × Harness

最后，我们用一个公式来总结第二部分：**Agent = Model × Harness**。

**Model（模型）** 提供预训练知识和推理能力、遵循指令的能力、工具使用的准确性。这些由模型提供商决定，我们通常无法直接改进。你能做的就是选择更好的模型——比如从 Claude 3.5 Sonnet 升级到 Claude 4 Opus。

**Harness（框架）** 负责上下文管理和优化、工具设计和执行、循环控制和错误处理。这些是我们可以改进的部分。你可以优化上下文管理策略、改进工具设计、调整循环控制逻辑。

关键洞察是：**改进 Harness 可以将 Agent 准确率提升 2 倍**。即使模型不变，通过优化 Harness 也能显著提升 Agent 的表现。这意味着：不要只盯着模型——Harness 的改进空间可能更大。

这也是为什么这门课的重点是 Agent 系统工程——我们大部分能改进的都在 Harness 层面。

## 第 46 页：从一个 Agent 到多个 Agent

什么时候需要从单 Agent 升级到多 Agent？

**Single Agent（单 Agent）：** 一个 LLM 处理所有任务，使用简单的 ReAct 循环。适合简单、线性的任务。但上下文窗口是瓶颈——所有信息都要塞进一个窗口。当任务变复杂时，上下文窗口很快就会被填满。

**Multi-Agent（多 Agent）：** 多个 specialized Agent 协作，并行处理不同子任务。适合复杂、多维度的任务。但通信和协调是新的挑战。多 Agent 系统需要解决"谁做什么"、"怎么通信"、"怎么协调"等问题。

重要提醒：**多 Agent 不是银弹——只有在单 Agent 不够时才引入**。如果单 Agent 能解决问题，就不要过度工程化。多 Agent 系统的复杂度远高于单 Agent——通信开销、协调成本、调试难度都会增加。


---

## 第 47 页：多Agent架构模式

多 Agent 系统有三种常见的架构模式：

**Pipeline（流水线）模式：** Agent A 的输出是 Agent B 的输入，顺序处理。比如"研究 Agent -> 写作 Agent -> 审校 Agent"。每个 Agent 专注于一个阶段。适合有明确阶段划分的任务，比如内容创作流程。优点是职责清晰，缺点是速度慢（必须等前一步完成）。

**Router（路由器）模式：** 一个调度 Agent 分析任务类型，分发给专家 Agent。比如 Router Agent 收到"帮我审查代码并写测试"的请求，将代码审查部分发给 Code Review Agent，将测试编写部分发给 Test Writer Agent。适合任务类型多样的场景。优点是专业化程度高，缺点是需要一个智能的 Router。

**Worker Pool（工人池）模式：** 多个相同的 Agent 并行处理同类子任务。比如 100 个文件需要 lint 检查，分配给 10 个 Worker Agent 并行处理，每个处理 10 个文件。适合可并行的大批量任务。优点是速度快（10 倍加速），缺点是需要同步和汇总结果。

选择模式的关键问题：任务是否有可并行性？是否需要专业化？需要就选 Router 或 Worker Pool，不需要就保持 Pipeline 或单 Agent。
---

## 第 48 页：何时以及为什么拆分工作

拆分工作的六个理由：

**并行性：** 子任务可以独立执行，并行加速。比如同时审查 5 个文件，比一个一个审查快 5 倍。

**专业化：** 不同 Agent 使用不同的 prompt、工具、模型。比如一个 Agent 专门写代码（用代码模型），另一个专门写测试（用测试模型），第三个专门写文档（用文档模型）。

**上下文隔离：** 避免单个 Agent 的上下文窗口过载。每个 Agent 只关注自己的子任务，上下文窗口不会被无关信息填满。

**故障隔离：** 一个 Agent 失败不影响其他 Agent。比如代码审查 Agent 出错了，测试生成 Agent 还能继续工作。

**可扩展性：** 按需添加更多 Agent 处理更大的任务。比如从 3 个 Agent 扩展到 10 个 Agent 来处理更大的代码库。

**人类协作：** 不同 Agent 对接不同的利益相关者。比如前端 Agent 对接前端开发者，后端 Agent 对接后端开发者。

---

## 第 49 页：设计多 Agent 系统的三个关键问题

设计多 Agent 系统需要回答三个关键问题：

**1. 如何分解任务？** 将大任务拆分成哪些子任务？粒度如何？是静态分解还是动态分解？比如"开发一个网站"可以拆分为"设计 UI"、"实现前端"、"实现后端"、"编写测试"——但粒度可以再细，也可以更粗。

**2. Agent 之间如何通信？** 使用什么媒介、通道、消息格式和语义？比如 Agent 之间是通过共享文件通信，还是通过消息队列？消息是自然语言还是 JSON？

**3. 如何协调和同步？** 如何处理依赖关系、冲突和失败？比如前端 Agent 需要等后端 Agent 完成 API 后才能开始集成测试——这就是依赖关系。

这三个问题决定了多 Agent 系统的架构和性能。回答好了这三个问题，系统设计就成功了一半。

---

## 第 50 页：任务分解：静态 vs 动态

任务分解有两种方式：

**静态分解：** 任务开始前就确定子任务，固定的 Agent 数量和角色。适合结构化、可预测的任务。例如代码审查流水线：lint 检查 → 风格检查 → 安全检查 → 测试覆盖检查，每个步骤由一个专门的 Agent 负责。静态分解的优点是可预测——你知道会有哪些 Agent、每个 Agent 做什么。缺点是缺乏灵活性——如果任务变化了，静态分解就不适用了。

**动态分解：** 运行时决定如何拆分，Agent 数量可变。适合开放式、探索性任务。例如研究助手：根据问题的复杂度动态决定需要多少个 Agent、每个 Agent 负责什么。动态分解的优点是灵活——可以根据实际情况调整。缺点是不可预测——你不知道最终会有多少个 Agent。

权衡：静态更可预测，动态更灵活。选择哪种取决于任务的性质。

---

## 第 51 页：Agent 通信的四个维度

Agent 之间的通信可以从四个维度来设计：

**1. 媒介（Medium）：** 消息通过什么传递？共享内存/文件（比如一个共享的 JSON 文件）、消息队列（比如 Redis Pub/Sub）、API 调用（比如 HTTP REST）。选择取决于速度和持久性需求。

**2. 通道（Channel）：** 如何组织和路由消息？点对点（Agent A 直接发消息给 Agent B）、广播（Agent A 发消息给所有 Agent）、发布-订阅（Agent A 发布到某个主题，订阅该主题的 Agent 收到消息）。

**3. 格式（Format）：** 消息的结构是什么？自然语言（灵活但可能歧义）、JSON/结构化数据（精确但不够灵活）、混合（比如 JSON 包裹自然语言）。

**4. 语义（Semantics）：** 消息的含义是什么？请求/响应（Agent A 请求，Agent B 响应）、事件通知（Agent A 通知 Agent B 某事发生了）、状态更新（Agent A 更新自己的状态，其他 Agent 可以看到）。

这四个维度的选择决定了 Agent 间通信的效率和可靠性。

---

## 第 52 页：A2A 协议

A2A（Agent-to-Agent）协议是 Agent 间通信的标准协议。它由 Google 在 2025 年提出，旨在解决不同 Agent 系统之间的互操作性问题。

**Agent Card** 描述 Agent 的能力，包括输入/输出格式、可用的技能和工具。它类似于"名片"或"API 文档"，让其他 Agent 知道这个 Agent 能做什么。比如一个代码审查 Agent 的 Agent Card 会说"我接受代码 diff 作为输入，输出审查报告"。

A2A 有三个核心抽象：

**Task（任务）：** Agent 处理的工作单元。每个 Task 有唯一 ID、状态、输入和输出。

**Message（消息）：** Agent 间的通信内容。Message 可以是文本、文件或其他格式。

**Artifact（产物）：** 任务产生的输出。比如代码审查 Task 的 Artifact 是审查报告。

A2A 的价值在于：**让不同厂商的 Agent 可以互操作**。就像 HTTP 让不同的 Web 服务器可以互操作一样。有了 A2A，一个公司开发的 Agent 可以和另一个公司开发的 Agent 无缝协作。


---

## 第 53 页：A2A消息示例

让我们通过具体的 JSON 示例来理解 A2A 协议的工作方式。

**Agent Card 示例：** 一个代码审查 Agent 的名片：name 是 "code-reviewer"，description 是"代码审查专家"，skills 包括 bug-detection、style-check、security-audit，input 是 diff 或文件路径，output 是审查报告 JSON。其他 Agent 通过读取这张"名片"就知道这个 Agent 能做什么。

**Task 消息流示例：** 当另一个 Agent 想要请求代码审查时：

1. **创建任务：** 发送 type: "task", action: "review", input: "src/auth.py"
2. **执行中：** 收到 type: "status", state: "working" — 表示审查正在进行
3. **返回结果：** 收到 type: "artifact", findings: 3, severity: "medium" — 审查完成，发现 3 个问题

这三个步骤展示了 A2A 的核心交互模式：Agent Card 是名片（让其他 Agent 知道你能做什么），Task 是对话（实际的工作请求和状态更新），Artifact 是交付物（最终的工作成果）。
---

## 第 54 页：Task 生命周期

Task 有两种生命周期：

**成功路径：** submitted → working → completed。Task 被提交后进入 working 状态，完成后进入 completed 状态。

**失败路径：** submitted → working → failed。如果执行过程中出错，Task 进入 failed 状态。

对于长时间运行的任务，A2A 支持异步执行和状态查询，可以跟踪进度。比如一个代码审查 Task 可能需要几分钟，你可以随时查询它的状态——是还在 working 还是已经 completed。

同时支持取消和超时：可以取消正在进行的任务（比如用户改变了主意），也可以设置超时限制（比如最多运行 10 分钟），防止任务无限运行。

---

## 第 55 页：MCP vs A2A

MCP 和 A2A 是两个不同层面的协议，很多人容易混淆它们。

**MCP：Agent ↔ 能力。** Agent 调用外部工具和资源，是单向的（Agent → Tool）。工具是被动的，不主动发起交互。MCP 类似"Agent 的手和眼"——Agent 通过 MCP 来操作外部世界。

**A2A：Agent ↔ Agent。** Agent 之间协作和通信，是双向的（Agent ⇄ Agent）。每个 Agent 都是主动的。A2A 类似"Agent 之间的对话"——Agent 通过 A2A 来互相交流。

总结：**MCP 让 Agent 能做事情，A2A 让 Agent 能协作**。一个 Agent 可以同时使用 MCP 和 A2A——用 MCP 调用工具做事，用 A2A 和其他 Agent 协作。

---

## 第 56 页：Agent 记忆设计问题

记忆系统设计需要回答一系列问题。这些问题看起来简单，但每一个都涉及复杂的权衡。

**值得保留吗？** 什么信息值得记住？什么可以遗忘？不是所有信息都值得跨会话保留——比如"用户今天问了天气"可能不值得记住，但"用户偏好中文回复"值得。

**变成什么形式？** 如何编码和组织记忆？纯文本？结构化 JSON？向量嵌入？图结构？不同形式有不同的优缺点。

**存在哪里？** 存储在哪里？文件？数据库？向量存储？选择取决于规模、检索需求和持久性要求。

**如何检索？** 精确匹配还是语义搜索？当记忆很多时，如何快速找到相关的？

**仍然有效吗？** 记忆是否过时？是否需要更新或删除？比如"项目使用 React 17"可能已经过时了（现在用 React 19）。

最后还有一个关键问题：**谁拥有这段记忆？** 是 Agent 自己（Harness 中的文件），还是外部服务（API 驱动的记忆系统）？

---

## 第 57 页：Agent 记忆设计问题（详细流程）

这一页展示了记忆设计的完整流程——从信息产生到最终消亡的完整生命周期。

第一行：**值得保留吗？** → 决策：写入或跳过 → **变成什么形式？** → 格式：编码/组织。这是记忆的"出生"阶段——决定什么信息值得记住，以及用什么形式记住。

第二行：**存在哪里？** → 后端：存储 → **当前任务需要吗？** → 任务：检索。这是记忆的"存储和检索"阶段——决定存在哪里，以及什么时候取出来用。

第三行：**能得出什么更广泛的教训？** → 反思/泛化 → **仍然有效吗？** → 状态：保留/更新/删除。这是记忆的"维护和消亡"阶段——定期审视记忆，更新过时的，删除无用的，泛化出更一般的教训。

最后还有一个所有权问题：**谁拥有这段记忆？** 这决定了记忆的可见性和生命周期管理。

这个流程涵盖了记忆从产生到消亡的完整生命周期。设计记忆系统时，每个环节都需要仔细考虑。

---

## 第 58 页：决策：何时写入记忆？

有三种写入记忆的决策模式：

**显式指令：** 用户说"记住这个"。优点是明确、可控——用户知道什么被记住了；缺点是依赖用户主动，容易遗漏重要信息。比如用户可能忘记说"记住我喜欢用 TypeScript"，但这个偏好很重要。

**自动检测：** 系统判断信息重要性，自动写入。优点是无需用户干预；缺点是可能误判，写入不重要的信息。比如系统可能把"用户今天问了天气"也记住了，但这没什么用。

**混合模式：** 自动检测 + 用户确认。系统检测到重要信息后，询问用户是否要记住。优点是平衡了自动化和控制；这是推荐的方案。比如系统发现"用户偏好中文回复"，会问"要不要记住这个偏好？"

关键问题始终是：**什么信息值得跨会话保留？** 这个问题的答案因项目而异——有些项目需要记住很多细节，有些只需要记住几个关键偏好。

---

## 第 59 页：格式：如何组织记忆？

记忆有四种组织格式：

**纯文本（Markdown）：** 人类可读、可编辑，易于 diff 和版本控制，适合规则和偏好。例如 CLAUDE.md。优点是可以直接用文本编辑器打开修改，可以 git 追踪变更历史。缺点是难以做复杂查询。

**结构化（JSON/YAML）：** 机器可解析，支持复杂查询，适合事实和数据。例如配置文件。优点是可以程序化查询（比如"找到所有 type=bug 的记录"）。缺点是人类直接阅读和编辑不太方便。

**向量嵌入：** 用于语义搜索，适合大量非结构化记忆。将文本转换为向量，通过相似度搜索找到相关记忆。比如把"用户偏好中文回复"转换为一个 1536 维的向量，搜索"语言偏好"时就能找到它。

**图结构：** 用于关系推理，适合实体和关系。比如"用户 A 在项目 B 中使用了技术 C"这样的三元组。图结构可以做多跳推理——比如"用户 A 用过哪些技术？"

---

## 第 60 页：如何存储记忆？

四种存储后端：

**纯文本文件：** CLAUDE.md、scratchpad。易于检查、diff 和搜索。适合小到中等规模的记忆。你可以直接用 `cat` 或 `grep` 来查看和搜索。

**键值或关系数据库：** Redis、SQLite、Postgres JSONB。支持精确查找、过滤、事务。适合结构化记忆。比如用 SQLite 存储所有的项目配置，用 SQL 查询特定配置。

**向量存储：** pgvector、Chroma、Pinecone。支持精确或近似相似度搜索。适合大量非结构化记忆的语义检索。比如用 Chroma 存储所有的项目知识，搜索"如何部署"时能找到相关的记忆。

**图数据库：** Neo4j、FalkorDB（Graphiti）。支持关系查询和多跳遍历。适合实体关系复杂的记忆场景。比如用 Neo4j 存储所有的项目实体和关系，查询"项目 A 依赖了哪些服务"。

选择哪种后端取决于记忆的规模、结构和检索需求。对于大多数项目，纯文本文件就够了；当记忆变多变复杂时，才需要考虑更高级的存储方案。

---

## 第 61 页：如何检索记忆？

检索记忆有四种方式：

**精确匹配：** 关键词搜索、ID 查找、过滤条件。快速、准确，但需要知道确切的关键词。比如搜索"CLAUDE.md"能找到这个文件，但搜索"项目配置"可能找不到。

**语义搜索：** 向量相似度、理解意图、模糊匹配。灵活、智能，但需要向量索引。比如搜索"项目配置"能找到 CLAUDE.md，即使文件名和内容里没有"配置"这个词。

**混合检索：** 结合精确和语义，先过滤再排序。先用精确匹配缩小范围，再用语义搜索排序。这是目前最实用的方案——兼顾速度和准确性。

**检索管线：** 查询 → 检索 → 重排 → 截断 → 注入上下文。这是一个完整的检索流程，每一步都有优化的空间。比如"重排"步骤可以用一个更强大的模型来重新排序检索结果。

---

## 第 62 页：遗忘是一等记忆操作

遗忘和记忆同样重要。为什么要遗忘？

**信息过时：** 项目迁移后，旧的配置信息就没用了。比如项目从 Webpack 迁移到了 Vite，那"如何配置 Webpack"的记忆就应该被删除或更新。

**避免上下文污染：** 不相关的记忆会干扰 Agent 的判断。比如一个前端项目的记忆不应该出现在后端项目的上下文中。

**保护隐私：** 敏感数据不应该长期保留。比如用户的密码、API 密钥等。

**减少噪音：** 提高检索质量，让相关记忆更容易被找到。记忆越多，检索的噪音越大。

遗忘策略有四种：

**TTL（Time To Live）：** 设置有效期，过期自动删除。比如"临时配置"的 TTL 是 7 天。

**LRU（Least Recently Used）：** 最近最少使用的记忆优先删除。这类似于操作系统的内存管理。

**显式删除：** 用户或 Agent 主动删除。比如用户说"忘记我的语言偏好"。

**自动清理：** 定期扫描和归档。比如每月清理一次超过 90 天未使用的记忆。

主动管理记忆的生命周期，和写入记忆一样重要。

---

## 第 63 页：谁拥有记忆？

记忆的所有权有两种模式：

**Agent 拥有：** Harness 中的文件，如 CLAUDE.md、Agent scratchpad、任务笔记。Harness 将记忆持久化到磁盘，LLM 和记忆文件之间是双向交互的——LLM 可以读取记忆，也可以修改记忆。这种模式简单、透明，但记忆只在单个 Agent 内可见。

**专用记忆系统：** Agent 调用的服务，如 Mem0、Graphiti、supermemory。记忆是 API，跨 Agent 和会话共享。LLM 通过 API 调用记忆层，记忆层是独立的服务。这种模式更强大——记忆可以跨多个 Agent 和会话共享，但复杂度也更高。

选择哪种模式取决于需求：如果需要简单的、项目级的记忆，用 Agent 拥有的文件就够了；如果需要复杂的、跨项目的记忆系统，用专用记忆系统更合适。

---

## 第 64 页：专用记忆系统

三个主流的专用记忆系统：

**Mem0（以事实为中心）：** 输入是消息，按用户、Agent 或运行分域。检索使用向量搜索加过滤，可选图记忆。例如记住"使用 SGLang 做模型服务"这样的事实。Mem0 的核心是"事实提取"——从对话中提取关键事实并存储。

**Graphiti（以事件为中心）：** 输入是事件和观察，构建知识图。检索使用图遍历加向量搜索。例如记录"用户在 3 月 15 日决定迁移到 Postgres"这样的事件。Graphiti 的核心是"知识图谱"——把事件和实体组织成图结构。

**supermemory（以对话为中心）：** 输入是完整对话，按时间索引。检索使用时间窗口加语义搜索。例如检索"上周关于 API 设计的讨论"。supermemory 的核心是"对话索引"——把完整对话按时间组织，支持时间范围检索。

三个系统各有侧重，选择取决于你的记忆主要是事实、事件还是对话。


---

## 第 65 页：记忆系统对比

让我们通过一个对比表来更清晰地理解三个记忆系统的区别。

**核心模型：** Mem0 用事实三元组，Graphiti 用知识图谱，supermemory 用对话时间线。

**最佳场景：** Mem0 适合用户偏好和事实（如"用户偏好 Python"），Graphiti 适合复杂关系推理（如"3月决定迁移数据库"），supermemory 适合对话回顾（如"上周讨论 API 设计"）。

**检索方式：** Mem0 用向量搜索加过滤，Graphiti 用图遍历加向量搜索，supermemory 用时间窗口加语义搜索。

**更新方式：** Mem0 增量更新事实，Graphiti 添加节点和边，supermemory 追加对话。

**如何选择？**

选 Mem0 如果你主要需要记住**事实**：用户偏好、项目配置、技术栈选择。Mem0 的事实提取能力最强。

选 Graphiti 如果你需要**关系推理**：实体之间的复杂关系、事件的时间线、决策的因果关系。Graphiti 的知识图谱支持多跳推理。

选 supermemory 如果你需要**对话回顾**：上周讨论了什么、上个月做了什么决策。supermemory 的时间线索引最适合按时间检索。

关键原则：先想清楚你要记住什么类型的信息，再选择对应的记忆系统。

## 第 66 页：记忆设计清单

设计记忆系统时，用这个清单来检查：

**决策层：** 什么信息值得记住？谁决定写入（用户/Agent/自动）？如何处理冲突的记忆？比如用户说"记住 X"，但 Agent 已经记住了"非 X"——怎么处理？

**格式层：** 使用什么编码格式？如何组织结构？是否需要元数据（时间、来源）？比如每条记忆是否需要记录"什么时候写入的"和"从哪里学到的"。

**存储层：** 选择什么后端？如何备份和恢复？跨设备同步？比如用户的记忆需要在本地电脑和公司电脑之间同步。

**检索层：** 精确还是语义搜索？如何排序和过滤？如何注入上下文？比如检索到的记忆是按相关性排序还是按时间排序？

这个清单覆盖了记忆设计的四个关键层面。设计记忆系统时，逐条检查这个清单可以确保不遗漏重要问题。

## 第 67 页：Part 4 章节页

最后一部分：可靠性。Agent 系统在实际使用中会面临各种故障，如何让它可靠地工作？

这部分是最实际的部分。前面讲的所有内容——Agent 循环、工具设计、多 Agent、记忆系统——都要在可靠性这个前提下才能发挥作用。一个不可靠的 Agent 系统，再好的设计也没有用。

---

## 第 68 页：为什么可靠性是个问题？

Agent 系统面临一个根本性的挑战：**错误复合效应**。

每一步都有失败概率，多步任务的失败率会指数增长。这是一个数学事实，不是工程问题——无论你多么小心，只要每一步有失败概率，多步之后整体失败率就会急剧上升。

举个例子：
- 单步准确率 95%——看起来很高
- 5 步任务：0.95^5 = 77%——还可以接受
- 10 步任务：0.95^10 = 60%——已经开始不可靠了
- 20 步任务：0.95^20 = 36%——失败率比成功率高了
- 50 步任务：0.95^50 = 8%——几乎必然失败

即使每一步的准确率很高（95%），多步之后整体准确率也会急剧下降。这就是为什么 Agent 系统的可靠性如此重要——你需要专门设计可靠性机制来对抗这个数学规律。

现实世界的挑战包括：工具调用可能失败、模型可能产生幻觉、上下文可能丢失关键信息、环境可能变化、用户意图可能模糊。Agent 系统必须在不确定性中可靠工作。


---

## 第 69 页：错误复合效应数学

让我们用更详细的数学来分析错误复合效应。

**左侧：准确率 vs 任务步数（单步准确率 p = 0.95）**
- 5步 -> 0.95^5 = 76.9% — 还可以接受
- 10步 -> 0.95^10 = 59.9% — 已经开始不可靠
- 15步 -> 0.95^15 = 46.3% — 失败率超过成功率
- 20步 -> 0.95^20 = 35.8% — 大约 2/3 会失败
- 30步 -> 0.95^30 = 21.5% — 几乎必然失败
- 50步 -> 0.95^50 = 7.7% — 几乎不可能成功

**右侧：20步任务，不同单步准确率的效果**
- p=0.90 -> 12.2% — 几乎必然失败
- p=0.95 -> 35.8% — 失败率比成功率高
- p=0.98 -> 66.8% — 刚刚过半
- p=0.99 -> 81.8% — 比较可靠
- p=0.999 -> 98.0% — 高度可靠

**关键结论：** 从 95% 到 99%，单步准确率只提升了 4 个百分点，但 20 步任务的成功率从 36% 跳到了 82%——提升了一倍多。这就是为什么提升每一步的可靠性比减少步数更重要。在工程实践中，这意味着：投入更多精力在工具的错误处理、模型的输出验证、上下文的精确管理上。
---

## 第 70 页：五层故障来源

故障来自五个层级，从上游到下游：

**1. 任务规格：** 需求不清、目标冲突。比如"优化性能"但没有具体指标——快多少？哪个页面？用什么指标衡量？这是最上游的故障，也是最难修复的——如果需求本身就有问题，后面的工作都是在错误的基础上进行的。

**2. Agent Harness：** 上下文管理、工具执行的问题。比如上下文截断导致关键信息丢失、工具超时导致任务中断。

**3. 模型：** 推理错误、幻觉。比如错误的代码逻辑、虚构的 API。模型失败是最难预测的——即使是最好的模型也会犯错。

**4. 工具：** API 失败、返回错误。比如数据库连接失败、文件不存在。工具失败是最常见的故障来源。

**5. 环境：** 外部变化、资源限制。比如网络中断、磁盘满、权限变化。环境失败通常不在我们的直接控制范围内。

理解这五层故障来源，才能有针对性地设计可靠性策略。每一层都需要不同的应对方式。

---

## 第 71 页：任务规格失败

任务规格失败是最上游的故障，也是最难修复的。

**模糊的需求：** "让网站更快"——多快？哪个页面？用什么指标衡量（首屏时间？TTFB？LCP？）？"修复 bug"——哪个 bug？如何复现？在什么环境下出现？"重构代码"——重构什么？目标是什么？减少代码重复？提高可读性？改善性能？

**冲突的目标：** "快速交付" vs "高质量"、"最小改动" vs "彻底修复"、"保持兼容" vs "使用新 API"。这些目标之间的冲突如果不提前解决，Agent 就会在两个方向之间摇摆，最终两边都做不好。

解决方案是：**明确、可衡量、可验证的任务定义**。每个任务都应该有清晰的输入、输出、约束和验收标准。比如"将首页 LCP 从 3.5 秒降低到 1.5 秒以下，使用 Lighthouse 测量"就是一个好的任务定义。

---

## 第 72 页：Agent Harness 失败

Harness 失败有三个主要方面：

**上下文管理：** 关键信息被截断（比如文件内容太长被截断，关键的错误信息在截断部分）、压缩丢失重要细节（比如压缩时把"不要修改 auth.ts"这个重要约束丢了）、上下文污染（无关信息占据了空间，导致相关信息被挤出）。

**工具执行：** 工具调用超时（比如 `bash` 命令运行超过 5 分钟）、返回结果过大（比如 `grep` 返回了几万行匹配）、权限不足（比如 Agent 没有写入某个目录的权限）。

**循环控制：** 无限循环（Agent 反复做同样的事——比如反复读同一个文件，每次都认为需要修改但实际没有）、过早终止（还没完成任务就停了——比如模型认为任务完成了但实际还有遗漏）、死锁（等待不可能的条件——比如等待一个永远不会返回 true 的条件）。

好消息是：**Harness 是我们可以控制和改进的部分**。通过优化 Harness，可以显著提升 Agent 的可靠性。

---

## 第 73 页：模型失败

模型失败有四种类型：

**推理错误：** 逻辑错误（错误的因果推理——比如"因为 A 在 B 之前发生，所以 A 导致了 B"）、数学计算错误（比如 0.1 + 0.2 = 0.30000000000000004）、忽略约束条件（比如系统提示说"不要修改 auth.ts"但模型还是修改了）、错误的代码逻辑（比如 off-by-one 错误、空指针引用）。

**幻觉：** 虚构不存在的 API（比如编造一个 `user.getProfile()` 方法，但实际 API 是 `user.profile()`）、编造函数或方法名、错误的文件路径（比如 `/src/components/Button.tsx` 但实际路径是 `/src/components/ui/Button.tsx`）、虚假的引用和来源。

**指令遵循失败：** 模型忽略系统提示词中的规则或约束。比如系统提示说"用中文回复"但模型用英文回复了。

**上下文理解错误：** 误解用户意图（比如用户说"修复这个 bug"指的是最近报告的 bug，但模型修复了一个旧的 bug），忽略关键上下文信息（比如上下文中明确说了"数据库密码是 xxx"但模型还是去问用户）。

模型失败是最难完全避免的，但我们可以通过验证和确认来降低其影响。

---

## 第 74 页：工具失败

工具失败是最常见的故障来源，有三种类型：

**API 失败：** 服务不可用（比如 GitHub API 宕机了）、速率限制（比如每分钟只能调用 60 次 API，超过了就被限流）、认证失败（比如 API token 过期了）。

**数据错误：** 文件不存在（比如 Agent 试图读取一个已经被删除的文件）、数据库连接失败（比如数据库服务器重启了）、返回格式错误（比如 API 返回了 HTML 而不是 JSON）。

**执行错误：** 命令超时（比如 `npm install` 运行了 10 分钟还没完成）、权限不足（比如 Agent 没有 root 权限，无法安装系统包）、资源限制（比如内存不够，进程被 OOM killer 杀掉了）。

工具失败是最常见的故障来源——因为工具依赖外部系统，而外部系统总是不可靠的。必须有重试和降级策略来应对工具失败。

---

## 第 75 页：环境失败

环境失败有四个方面：

**外部变化：** 文件被其他进程修改或删除（比如用户同时在编辑器中修改了同一个文件）、网络中断或不稳定（比如 Wi-Fi 断了）、依赖服务宕机（比如 npm registry 挂了）、配置被更改（比如环境变量被修改了）。

**资源限制：** 磁盘空间不足（比如 `node_modules` 占了太多空间）、内存耗尽（比如处理大文件时内存不够）、CPU 过载（比如编译大型项目时 CPU 100%）、端口冲突（比如 3000 端口已经被其他进程占用了）。

**权限问题：** 文件权限变化（比如 `chmod` 改了文件权限）、用户权限不足（比如普通用户无法执行 `sudo` 命令）、沙箱限制（比如 Agent 被限制在项目目录内，无法访问外部文件）。

**并发冲突：** 多个 Agent 同时修改同一资源（比如两个 Agent 同时修改同一个文件，导致冲突）。

环境失败通常不在我们的直接控制范围内，但可以通过监控和防御性编程来减少其影响。

---

## 第 76 页：为失败而设计

面对五层故障，我们有五种设计策略：

**1. 重试策略：** 指数退避重试（第一次等 1 秒，第二次等 2 秒，第三次等 4 秒……）、最大重试次数（比如最多重试 3 次）、区分可重试和不可重试错误。比如网络超时可以重试（可能是临时问题），但认证失败不应该重试（重试也不会成功）。

**2. 降级策略：** 工具失败时使用备选方案（比如主数据库挂了用备用数据库）、部分失败时继续执行（比如 5 个子任务中 1 个失败了，其他 4 个继续）、优雅降级而非完全失败（比如搜索功能挂了，显示"搜索暂时不可用"而不是整个页面崩溃）。

**3. 检查点：** 保存中间状态（比如每完成一个子任务就保存进度）、可以从失败点恢复（比如第 5 步失败了，从第 5 步重新开始而不是从头开始）、避免重复已完成的工作。长任务尤其需要检查点机制——一个运行 30 分钟的任务如果因为最后一步失败而需要从头开始，那代价太大了。

**4. 验证和确认：** 每步验证结果（比如写完文件后检查文件是否存在）、关键操作前确认（比如删除文件前问用户"确定要删除吗？"）、输出格式检查（比如检查模型输出的 JSON 是否合法）。在关键节点设置验证点，及时发现问题。

**5. 人类在环：** 关键决策请求确认（比如"我要修改 auth.ts，确定吗？"）、不确定时询问用户（比如"你说的'修复 bug'是指哪个 bug？"）、提供回退选项（比如"我做了这些修改，如果不满意可以撤销"）。让人类在关键时刻介入，是最后的保障。

## 第 77 页：总结

最后，我们来回顾一下四大部分的核心内容：

**Part 1: Agentic Loop** — 智能体循环是推理→行动→观察的循环；记忆系统包括 CLAUDE.md 和专用系统；扩展机制有 Skills、MCP、Hooks、Plugins 四种。核心公式：Agent = LLM + Tools + Loop。

**Part 2: Agent Loop & Tools** — ReAct Loop 让模型边想边做；工具设计要遵循原子性、明确性、安全性；上下文工程通过准入、卸载、转换、压缩四种策略管理有限的上下文窗口。核心公式：Agent = Model × Harness。

**Part 3: Multi-Agent & Memory** — 任务分解有静态和动态两种方式；通信设计从媒介、通道、格式、语义四个维度考虑；记忆设计涵盖决策、格式、存储、检索四个层面。核心协议：MCP（Agent ↔ 能力）和 A2A（Agent ↔ Agent）。

**Part 4: Reliability** — 错误复合效应导致多步任务失败率指数增长（0.95^50 = 8%）；故障来自规格、Harness、模型、工具、环境五层；为失败设计需要重试、降级、检查点、验证、人类在环五种策略。

最后记住这个公式：**Agent = Model × Harness，改进 Harness 是提升可靠性的关键**。
