## Slide 5 — Agent memory（Agent 记忆）

这一页定义了什么是 Agent memory。

画面中有一个图，展示了 **persistent state beyond context window**（超越上下文窗口的持久化状态）。

**核心概念**：Agent memory 是指那些**不放在当前对话上下文里，但 Agent 需要记住的信息**。

为什么要这样做？因为 LLM 的 Context Window 是有限的。如果你把所有历史信息都塞进上下文，很快就会超出限制。而且不是所有历史信息都同等重要——有些需要长期记住，有些用过就可以忘了。

所以我们需要一个**外部的记忆系统**，让 Agent 可以：
- **Store（存储）**：把重要信息存下来
- **Retrieve（检索）**：在需要的时候取出来
- **Forget（遗忘）**：把不需要的信息清除掉

这就像人类的大脑——你不会记住每一顿饭吃了什么，但你会记住重要的事件和学到的教训。

## Slide 6 — Agent memory design questions（Agent 记忆设计问题）

这一页提出了设计记忆系统时需要回答的**六个关键问题**，用一个流程图展示：

**1. Keeping?（记什么？）**：哪些信息值得记住？不是所有信息都需要存储。

**2. Format?（什么格式？）**：记住的信息用什么格式组织？是原始文本、摘要、还是结构化数据？

**3. Backend?（存在哪里？）**：用什么存储后端？文件、数据库、向量存储？

**4. Need it?（什么时候需要？）**：什么时候触发记忆检索？是每次对话都查，还是按需查询？

**5. Lesson?（学什么教训？）**：从过去的经验中提炼什么教训？

**6. Valid?（怎么验证？）**：怎么验证记忆是准确的、没有过时的？

这六个问题构成了记忆系统设计的完整框架。回答清楚这六个问题，你就有了一个完整的记忆系统设计方案。

## Slide 7 — Decision: when should something become memory?（决策：什么时候某件事应该成为记忆？）

这一页讨论的是第一个问题：**什么时候应该把信息存为记忆？**

画面中有一个光谱图，从 **Recall**（召回）到 **Precision**（精确）：

- **Recall 端**：记住 everything（所有东西）。好处是不会遗漏重要信息，坏处是存储成本高、检索噪声大。
- **Precision 端**：只记住 very important things（非常重要的东西）。好处是存储精简、检索准确，坏处是可能遗漏重要信息。

你需要在这两个极端之间找到平衡点。

**判断标准**：
- 这条信息未来会被用到吗？
- 不用记忆的话，Agent 能重新推导出来吗？
- 存储和检索的成本值得吗？

## Slide 8 — How to organize the memory?（怎么组织记忆？）

这一页讨论记忆的**组织格式**。画面中列出了四种格式，并给出了 SGLang 的例子：

**1. Raw events（原始事件）**：
直接存储原始的对话或操作记录。比如保存完整的用户消息和 Agent 回复。
- 优点：信息完整，没有损失
- 缺点：存储量大，检索时需要额外处理

**2. Unstructured summaries（非结构化摘要）**：
用自然语言总结关键信息。比如"用户偏好简洁的代码风格"。
- 优点：紧凑，易于理解
- 缺点：可能丢失细节，摘要质量依赖 LLM

**3. Structured state（结构化状态）**：
用结构化的格式（如 JSON、数据库记录）存储信息。比如 `{"preferred_language": "Python", "experience_level": "senior"}`。
- 优点：易于查询和更新，格式统一
- 缺点：需要预定义 schema，灵活性较低

**4. Knowledge graph（知识图谱）**：
用实体和关系来表示知识。比如"用户 A → 喜欢 → Python"、"项目 B → 使用 → React"。
- 优点：能表示复杂关系，支持推理
- 缺点：构建和维护成本高

选择哪种格式取决于你的应用场景。简单的场景用摘要就够了，复杂的场景可能需要知识图谱。

## Slide 9 — How to store the memory?（怎么存储记忆？）

这一页讨论记忆的**存储后端**。画面中列出了四种选择，并给出了具体的工具：

**1. Plain files（普通文件）**：
用 JSON、Markdown 等文件格式存储。
- 工具示例：本地文件系统
- 适合：小规模、简单的记忆

**2. KV/Relational DB（键值/关系型数据库）**：
用数据库存储结构化记忆。
- 工具示例：Redis（KV）、PostgreSQL（关系型）
- 适合：需要快速查询和更新的结构化记忆

**3. Vector store（向量存储）**：
把记忆编码成向量，用相似度搜索来检索。
- 工具示例：Pinecone、Weaviate、Chroma
- 适合：语义检索，比如"找到和这个问题最相关的记忆"

**4. Graph database（图数据库）**：
用图结构存储实体和关系。
- 工具示例：Neo4j
- 适合：知识图谱，需要查询复杂关系的场景

选择存储后端时，要考虑：数据规模、查询模式、延迟要求、成本等因素。

## Slide 10 — When memory should be used?（什么时候使用记忆？）

这一页讨论记忆检索的**触发时机**。画面中列出了三种方式：

**1. Automatic（自动）**：
每次对话都自动检索相关记忆。Agent 不需要显式请求，系统自动提供相关记忆。
- 优点：不会遗漏
- 缺点：可能引入不相关的噪声

**2. Runtime-controlled（运行时控制）**：
由运行时系统决定什么时候检索记忆。比如当对话超过一定长度，或者检测到用户提到了历史话题时触发。
- 优点：比全自动更智能
- 缺点：需要设计触发规则

**3. Model-controlled（模型控制）**：
由 LLM 自己决定什么时候需要检索记忆。Agent 在推理过程中主动请求检索。
- 优点：最灵活，由模型根据上下文判断
- 缺点：依赖模型的判断能力，可能遗漏

---

## Slide 11 — How to retrieve the memory?（怎么检索记忆？）

这一页讨论记忆的**检索机制**。

画面中有一个检索流水线（pipeline）的图，展示了从 Query（查询）到 Retrieved memories（检索到的记忆）的流程。

检索时需要考虑**五个信号（signals）**：

**1. Semantic match（语义匹配）**：
查询和记忆在语义上有多相关？用向量相似度来衡量。

**2. Scope（范围）**：
记忆的适用范围是什么？是全局记忆还是特定场景的记忆？

**3. Importance（重要性）**：
这条记忆有多重要？重要的记忆应该优先检索。

**4. Validity（有效性）**：
这条记忆还有效吗？有没有过时？

**5. Provenance（来源）**：
这条记忆从哪里来的？来源可靠的记忆更值得信任。

这五个信号综合起来，决定哪些记忆应该被检索出来提供给 Agent。

## Slide 12 — How to generalize from observations?（怎么从观察中泛化？）

这一页讨论的是**从具体经验中提炼通用知识**。

画面中给出了 vLLM/SGLang/TRT-LLM 的例子：

假设 Agent 观察到：
- "vLLM 在 A100 上推理速度比 H100 快 20%"
- "SGLang 的 prefix caching 对长上下文很有用"
- "TRT-LLM 的 batch size 对延迟影响很大"

Agent 可以从这些具体观察中泛化出通用知识：
- "GPU 型号对推理性能有显著影响"
- "缓存机制对长上下文场景很重要"
- "批处理参数需要针对具体硬件调优"

这种泛化能力让 Agent 不仅能记住具体事实，还能提炼出可迁移的经验。

## Slide 13 — Forgetting is a first-class memory operation（遗忘是一等记忆操作）

这一页强调：**遗忘和记忆一样重要**。

画面中有一个图，展示了记忆的生命周期：创建 → 使用 → 遗忘。

**为什么要遗忘？**
- 存储成本：不是所有记忆都值得永久保存
- 检索噪声：过多的记忆会降低检索质量
- 过时信息：有些记忆会随着时间变得不准确
- 隐私安全：敏感信息不应该永久保存

**遗忘策略**：
- **Time-based（基于时间）**：超过一定时间的记忆自动删除
- **Usage-based（基于使用）**：长期未被访问的记忆被清除
- **Importance-based（基于重要性）**：低重要性的记忆被优先遗忘
- **Explicit（显式）**：用户或系统主动删除特定记忆

遗忘不是失败，而是记忆系统的必要功能。

---

## Slide 14 — Memory needs valid time and provenance（记忆需要有效时间和来源）

这一页讨论记忆的两个关键属性：

**1. Valid time（有效时间）**：
每条记忆都应该有有效期。比如：
- "用户昨天说喜欢 Python"——这条记忆的有效期可能只有几天
- "项目的技术栈是 React"——这条记忆的有效期可能长达几个月

超过有效期的记忆应该被标记为可能过时，或者自动删除。

**2. Provenance（来源）**：
每条记忆都应该记录来源。比如：
- 这条记忆是从哪次对话中提取的？
- 是用户明确说的，还是 Agent 推断的？
- 来源的可靠性如何？

记录来源的好处：
- 可以追溯记忆的形成过程
- 可以评估记忆的可信度
- 出问题时方便调试

## Slide 15 — Who owns the memory?（谁拥有记忆？）

这一页讨论记忆的**所有权**问题。画面中列出了两种模式：

**1. Agent-owned（Agent 拥有）**：
记忆属于某个特定的 Agent。只有这个 Agent 能访问和修改自己的记忆。
- 优点：隔离性好，不会互相干扰
- 缺点：记忆不能共享，可能重复存储

**2. Dedicated memory system（专用记忆系统）**：
有一个独立的记忆系统，多个 Agent 可以共享访问。
- 优点：记忆可以共享，避免重复
- 缺点：需要处理并发访问、权限控制等问题

选择哪种模式取决于你的应用场景。如果 Agent 之间需要协作，专用记忆系统更合适；如果 Agent 之间独立工作，Agent-owned 更简单。

## Slide 18 — Failure modes（失败模式）

这一页开始进入可靠性部分，列出了 Agent 的**八种失败模式**：

**1. Hallucination（幻觉）**：
Agent 编造不存在的信息。比如引用不存在的论文，或者编造事实。

**2. Infinite Loops（无限循环）**：
Agent 陷入 ReAct 循环，不断重复同样的操作，永远无法完成任务。

**3. Tool Misuse（工具误用）**：
Agent 错误地使用工具。比如用错误的参数调用 API，或者在不应该使用工具的时候使用工具。

**4. Context Overflow（上下文溢出）**：
Agent 的对话历史超过了 Context Window 的限制，导致信息丢失或错误。

**5. Prompt Injection（提示注入）**：
恶意用户在输入中嵌入特殊的指令，操纵 Agent 的行为。比如"忽略之前的指令，做 XXX"。

**6. Data Leakage（数据泄露）**：
Agent 不小心泄露了敏感信息。比如在回复中包含其他用户的私人数据。

**7. Resource Exhaustion（资源耗尽）**：
Agent 消耗了过多的 token、API 调用次数、或计算资源，导致系统崩溃或成本爆炸。

**8. Cascade Failures（级联失败）**：
在多 Agent 系统中，一个 Agent 的错误传播到其他 Agent，导致整个系统崩溃。

理解这些失败模式是预防它们的第一步。

## Slide 20 — How to evaluate agent memory（怎么评估 Agent 记忆）

这一页讨论记忆的**评估维度**。画面中列出了四个维度：

**1. Recall（召回率）**：
Agent 能记住多少应该记住的信息？如果重要信息没有被记住，召回率就低。

**2. Precision（精确率）**：
检索出来的记忆有多少是相关的？如果检索出很多不相关的记忆，精确率就低。

**3. Latency（延迟）**：
检索记忆需要多长时间？如果检索太慢，会影响用户体验。

**4. Freshness（新鲜度）**：
记忆有多新？过时的记忆会降低 Agent 的表现。

评估不是一次性的，而是持续的过程。你需要建立一套评估体系，定期测试你的记忆系统。

## Slide 21 — Agent memory evaluation（Agent 记忆评估基准）

这一页介绍了一些**记忆评估的 Benchmark**：

**1. LoCoMo（Long-Context Conversational Memory）**：
评估 Agent 在长对话中的记忆能力。测试 Agent 是否能记住对话中提到的关键信息。

**2. LongMemEval**：
评估长期记忆的能力。测试 Agent 是否能跨多个 session 记住重要信息。

**3. BEAM**：
评估 Agent 的记忆、推理和规划能力。

这些 Benchmark 提供了标准化的测试集和评估指标，让你可以比较不同记忆系统的性能。

如果你要设计自己的记忆系统，可以先在这些 Benchmark 上测试，了解它的基线性能。
