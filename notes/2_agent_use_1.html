关键洞察

智能体不是一次性回答，而是一个循环：模型提议行动 → 执行器执行 → 结果折叠回上下文 → 模型再次推理，直到任务完成。

🔄 智能体循环

The Agentic Loop

① 模型提议

LLM 分析上下文，决定下一步行动：调用工具、读取文件、执行命令，或直接回答。

② 执行器执行

安全沙箱执行模型提议的操作：运行命令、读写文件、调用 API。结果被捕获。

③ 结果折叠

执行结果作为新的上下文消息追加，模型基于新信息继续推理。循环重复直到任务完成。

模型 ≠ 执行器。模型只"提议"，执行器负责"执行"。
📚 上下文

Context Before You Type

在你输入任何内容之前，系统已经组装了多层上下文：

⑥ 自动记忆 — 跨会话的学习和偏好
⑤ CLAUDE.md — 项目/用户/组织级指令
系统提示词 — 模型行为规则
③ 工具定义 — 可用工具的 JSON Schema
对话历史 — 之前的消息交换
① 你的提示词 — 当前输入
每一层都消耗上下文窗口，需要精心管理
🔒 隐私

不会发送你的整个仓库

✅ 实际发送的

  • 系统提示词（固定模板）
  • 工具定义（JSON Schema）
  • CLAUDE.md 指令文件
  • 对话历史消息
  • 模型请求读取的特定文件内容

❌ 不会发送的

  • 整个代码仓库
  • 未引用的源文件
  • 二进制文件和依赖
  • .git 目录
  • 本地环境变量和密钥
模型只看到它需要看到的内容，而非全部
⚙️ 分离架构

Model Proposes · Harness Executes

🧠 模型（LLM）

  • 分析上下文和提示词
  • 决定下一步行动
  • 生成工具调用请求
  • 不能直接执行任何操作
  • 只输出"提议"

🔧 执行器（Harness）

  • 接收模型的提议
  • 在安全沙箱中执行
  • 检查权限和约束
  • 捕获输出和错误
  • 将结果返回给模型
这种分离是安全的关键：模型有想法，但没有手
🔁 多次推理

One Prompt, Many Inferences

一个用户提示词可能触发模型的多次推理调用：

用户提示词
→
推理 #1：读取文件
→
推理 #2：分析代码
→
推理 #3：修改文件
→
推理 #4：运行测试

💡 关键理解

每次推理都会消耗 token。复杂的任务可能需要 10+ 次模型调用。理解这一点有助于你写出更高效的提示词。

好的提示词 = 减少不必要的推理轮次
🔐 权限系统

Permissions — 四个级别

🟢 自动允许

安全操作自动执行，无需确认。如读取文件、搜索代码。

🟡 自动允许 + 通知

操作会执行，但会在界面显示通知。如写入文件、创建目录。

🟠 每次询问

每次执行前都需要用户确认。如运行 shell 命令、安装依赖。

🔴 始终拒绝

操作被完全禁止。如删除文件、推送代码到远程仓库。

你可以在设置中自定义每个工具的权限级别
📈 上下文管理

Context Grows · Then Compacted

📈 上下文增长

每次推理的结果都追加到对话历史中。随着任务进行，上下文不断增长：

  • 文件内容被读取并加入
  • 命令输出被追加
  • 工具调用结果被记录

️ 上下文压缩

当接近窗口限制时，系统会压缩早期内容：

  • 早期对话被摘要化
  • 详细输出被截断
  • 保留关键决策和结论
压缩会丢失细节 — 这就是为什么记忆系统很重要

💡 关键概念

Context Is One Type of Memory

  • 智能体在会话之间是无状态的 — 每次会话从零开始
  • 实际上，"记忆"只是在会话启动时加载的文件
每一次记忆创建，都是关于"什么将被永远重新读取"的决策。

👁️ 上下文：工作记忆

模型此刻能看到的内容 — 随会话结束而消失。

📦 持久记忆

在会话结束后幸存，下次启动时重新加载的内容。

❓ 为什么需要记忆

Why Agents Need Memory

🔁 重复指令

每次会话都要重新解释相同的设置

📉 丢失的决策/假设

当窗口压缩时，"为什么"消失了

🔍 重复发现

智能体重新读取相同文件来重新学习布局

⚠️ 不一致行为

不同会话做出不同的选择

记忆是指令变为惯例的方式。

️ 内容指南

What Belongs in CLAUDE.md

✅ 应该包含

  • 命令：如何运行测试、构建、lint
  • 硬约束：永不提交到 main、永不编辑生成文件
  • 事实：模型无法廉价推断的信息：布局、所有权、注意事项

❌ 不应包含

  • 模型已经知道的语言或框架知识
  • linter 或 formatter 已经执行的风格偏好
  • 长散文、变更日志、任何秘密信息
大小
每文件 <200 行
结构
Markdown 标题和列表
具体性
具体规则，非模糊描述
一致性
无矛盾或过时规则
上下文是租来的，记忆是拥有的 — 谨慎选择你拥有的内容。
📂 规则拆分

Getting Too Long?
Split Into .claude/rules/

每个文件一个主题 — 每条规则只在相关时加载。

📄 每个文件一个主题

🏷️ 添加 paths: frontmatter

仅在 Claude 接触匹配文件时加载（无 paths: 则每次会话都加载）。

📁 示例

💡 要点

  • 范围化规则保持上下文窗口小
  • 只有匹配工作的规则被加载
  • CLAUDE.md 保持简短；细节放在规则中

🔍 检索

Retrieval Uses an Index

当上下文中的信息不够时，智能体通过索引检索更多内容：

  1. 查询理解 — 分析你的问题，提取关键词和意图
  2. 索引查找 — 在代码索引中搜索匹配的文件和符号
  3. 相关性排序 — 对候选结果按相关性打分排序
  4. 内容加载 — 读取最相关的文件内容到上下文
  5. 推理继续 — 模型基于新加载的信息继续推理

Extending an Agent

扩展智能体的能力边界

四种机制：Skill · MCP · Hook · Plugin

四种机制

Four Mechanisms to Extend an Agent

SKILL

技能

可复用的过程模板。将复杂工作流封装为命名步骤，按需加载到上下文中。

MCP

模型上下文协议

外部能力层。通过标准协议连接外部服务，扩展智能体的工具集。

HOOK

钩子

生命周期自动化。在特定事件（工具调用前后）自动执行脚本。

PLUGIN

插件

打包层。将 Skill + MCP + Hook 组合为可分发的独立单元。

🔌 扩展点

Extension Points in Agent Loop

SKILL 在模型推理前注入过程模板到上下文
MCP 在工具定义阶段注册外部工具
HOOK 在工具调用前/后自动触发脚本
PLUGIN 打包以上所有机制为一个单元
每种机制在循环的不同位置介入
📦 示例

Release Workflow Example

一个真实的发布流程如何组合多种机制：

  1. Hook（预检查） — 发布前自动运行 lint 和测试，确保代码质量
  2. Skill（流程模板） — 加载 "release" 技能，包含版本号更新、changelog 生成等步骤
  3. MCP（外部服务） — 调用 GitHub API 创建 Release，调用 Slack API 发送通知
  4. Plugin（打包） — 以上所有打包为 "release-plugin"，团队共享
📋 技能

Skills as Reusable Procedures

什么是技能？

  • 命名化的工作流模板
  • 包含步骤、约束和上下文
  • 按需加载，不占用常驻上下文
  • 可以被用户或插件定义

技能 vs 提示词

  • 提示词：一次性的指令
  • 技能：结构化的、可复用的过程
  • 技能包含条件逻辑和步骤顺序
  • 技能可以被版本控制和共享
技能将"知道怎么做"变为"可重复执行的标准流程"
📐 结构

Skill Structure

📄 技能文件

--- name: code-review description: 代码审查流程 --- # 代码审查技能 ## 步骤 1. 读取变更的文件 2. 检查代码风格 3. 验证测试覆盖 4. 生成审查报告

🧱 组成部分

  • Frontmatter：元数据（名称、描述、触发条件）
  • Instructions：详细的步骤说明
  • Constraints：必须遵守的规则
  • Examples：输入输出示例
  • Context：需要的背景信息
💰 成本

Skill Invocation & Context Cost

✅ 优势

  • 按需加载，不常驻上下文
  • 结构化指导减少推理轮次
  • 可复用，一次编写多次使用
  • 团队共享，保持一致性

⚠️ 成本

  • 加载时消耗上下文窗口
  • 复杂技能可能很长
  • 过多技能增加管理负担
  • 需要维护与更新
好的技能设计 = 最大价值 / 最小上下文占用

⚙️ MCP 调用

How MCP Tool Call Works

  1. 工具注册 — MCP 服务器启动时，向智能体注册可用工具及其 JSON Schema
  2. 模型决策 — 模型在推理中决定调用某个 MCP 工具，生成工具调用请求
  3. 协议传输 — 请求通过 MCP 协议（JSON-RPC）发送到 MCP 服务器
  4. 外部执行 — MCP 服务器在外部环境中执行操作（查询数据库、调用 API 等）
  5. 结果返回 — 结果通过协议返回，折叠回上下文，模型继续推理
🪝 钩子

Hooks as Lifecycle Automation

🔔 触发时机

  • Pre-tool：工具调用之前
  • Post-tool：工具调用之后
  • Pre-turn：每轮推理之前
  • Post-turn：每轮推理之后

📝 典型用途

  • 自动运行 lint / 格式化
  • 工具调用前的权限检查
  • 执行后的通知发送
  • 自动提交 / 创建 PR
# .claude/hooks/pre-tool-bash.sh if [[ "$TOOL" == "Bash" ]]; then echo "⚠️ 即将执行: $COMMAND" fi
📦 插件

Plugins as Packaging Layer

插件 = Skill + MCP + Hook 的组合打包

📋 包含技能

🔌 包含 MCP

外部服务连接配置

🪝 包含钩子

自动化脚本

插件让团队可以一键安装完整的智能体增强方案
🧩 协同

How Four Mechanisms Fit Together

PLUGIN 打包层 — 将以下所有组合为可分发单元
SKILL 过程层 — 定义"做什么"和"怎么做"
MCP 能力层 — 提供外部工具和服务
HOOK 自动化层 — 在生命周期事件中触发
从底层到顶层：Hook → MCP → Skill → Plugin

MCP 基础

MCP: What and Why

什么是 MCP？

Model Context Protocol（模型上下文协议）是一个开放标准，定义了 AI 模型与外部数据源和工具之间的通信方式。

类比：USB 之于外设，MCP 之于 AI 工具。

❓ 为什么需要 MCP？

  • 标准化：统一的工具连接协议
  • 解耦：模型与工具独立演进
  • 生态：一次集成，多模型复用
  • 安全：明确的权限和沙箱边界

🔑 核心原语

MCP Three Core Primitives

🔧 Tools 工具

模型可以调用的函数。每个工具有名称、描述和 JSON Schema 参数定义。

示例：query_database、send_slack_message

📚 Resources 资源

模型可以读取的数据源。类似文件路径，但可以是任何结构化数据。

示例：database://users、config://app

💬 Prompts 提示词

预定义的提示词模板。Server 可以提供可复用的提示词供模型使用。

示例：code_review_prompt、debug_assistant

📝 完整流程示例

  1. 用户使用 Prompt 模板发起代码审查请求
  2. MCP Server 通过 Resource 读取仓库配置和代码规范
  3. 模型决定调用 Tool 查询数据库获取变更历史
  4. 模型调用另一个 Tool 在 GitHub 上创建审查评论
  5. 结果通过协议返回，折叠回上下文
🔒 安全

MCP Security

️ 安全机制

  • 显式授权：每个工具调用需要用户或策略授权
  • 沙箱执行：MCP Server 在隔离环境中运行
  • 最小权限：工具只暴露必要的操作
  • 审计日志：所有工具调用可追溯

️ 注意事项

  • 只安装可信的 MCP Server
  • 审查工具的权限范围
  • 注意数据流向（哪些数据发送给外部服务）
  • 定期更新 MCP Server 以修复安全漏洞
MCP 扩展了能力边界，但也扩展了攻击面 — 安全不可忽视
