SCALING

从一个 Agent 到多个 Agent

Single Agent 单 Agent

  • 一个 LLM 处理所有任务
  • 简单的 ReAct 循环
  • 适合简单、线性任务
  • 上下文窗口是瓶颈

Multi-Agent 多 Agent

  • 多个 specialized Agent 协作
  • 并行处理不同子任务
  • 适合复杂、多维度任务
  • 通信和协调是挑战
多 Agent 不是银弹 — 只有在单 Agent 不够时才引入
WHEN & WHY

何时以及为什么拆分工作？

并行性

子任务可以独立执行，并行加速

专业化

不同 Agent 使用不同的 prompt、工具、模型

上下文隔离

避免单个 Agent 的上下文窗口过载

故障隔离

一个 Agent 失败不影响其他 Agent

可扩展性

按需添加更多 Agent 处理更大任务

人类协作

不同 Agent 对接不同的利益相关者

KEY QUESTIONS

设计多 Agent 系统的三个关键问题

1. 如何分解任务？

将大任务拆分成哪些子任务？粒度如何？静态还是动态？

2. Agent 之间如何通信？

使用什么媒介、通道、消息格式和语义？

3. 如何协调和控制？

谁来分配任务？如何处理冲突和失败？如何聚合结果？

DECOMPOSITION

任务分解

分解策略

  • 功能分解：按功能模块拆分
  • 数据分解：按数据分片拆分
  • 时间分解：按时间阶段拆分
  • 空间分解：按地理/逻辑位置拆分

分解原则

  • 子任务应高内聚
  • 子任务间应低耦合
  • 每个子任务应有明确输入输出
  • 子任务应可独立验证
SUB-TASKS

子任务设计考虑

依赖性

  • 子任务之间是否有依赖？
  • 依赖是线性的还是网状的？
  • 能否并行执行？

信息流

  • 子任务需要共享什么信息？
  • 信息是单向还是双向流动？
  • 如何避免信息过载？

错误传播

  • 一个子任务失败如何影响其他？
  • 是否需要回滚机制？

聚合策略

  • 如何合并子任务的结果？
  • 冲突如何解决？
GRANULARITY

粒度权衡

粗粒度

  • 子任务数量少
  • 每个子任务复杂度高
  • 通信开销低
  • 并行度低
  • 适合：简单任务、强依赖

细粒度

  • 子任务数量多
  • 每个子任务复杂度低
  • 通信开销高
  • 并行度高
  • 适合：复杂任务、弱依赖
找到通信开销和并行收益之间的平衡点
STATIC vs DYNAMIC

静态 vs 动态分解

静态分解

  • 任务开始前就确定子任务
  • 结构固定，不可更改
  • 易于理解和调试
  • 适合：结构化、可预测的任务
Plan → [Task1, Task2, Task3] → Execute all → Aggregate

动态分解

  • 运行时根据情况决定
  • 灵活适应变化
  • 更复杂，难以预测
  • 适合：开放域、不确定的任务
Plan → Task1 → Observe → Re-plan → [Task2a, Task2b] → Execute → ...
FAILURES

分解失败的六种类型

1. Over-decomposition

过度分解，子任务太小，通信开销超过收益

2. Under-decomposition

分解不足，子任务太大，失去并行优势

3. Wrong boundaries

边界错误，相关功能被拆分，无关功能被合并

4. Missing dependencies

遗漏依赖，子任务执行顺序错误

5. Information loss

信息丢失，分解时丢失关键上下文

6. Aggregation failure

聚合失败，无法正确合并子任务结果

通信的四个维度

1. Medium 媒介

消息通过什么载体传递？

  • 直接消息传递
  • 共享黑板/数据库
  • 事件总线

2. Channel 通道

使用什么通信协议？

  • 同步 vs 异步
  • 点对点 vs 广播
  • 持久化 vs 临时

3. Format 格式

消息的结构化程度？

  • 自然语言
  • 结构化数据（JSON）
  • 混合格式

4. Semantics 语义

消息的含义和意图？

  • 请求/响应
  • 通知/事件
  • 命令/确认
MEDIUM

通信媒介

直接消息传递

Agent A 直接发送给 Agent B

  • 简单直接
  • 需要知道对方地址
  • 适合：点对点通信

共享黑板

所有 Agent 读写共享空间

  • 解耦发送者和接收者
  • 需要冲突解决
  • 适合：协作任务

事件总线

通过事件系统广播和订阅

  • 高度解耦
  • 支持一对多
  • 适合：事件驱动架构
CHANNELS

通信通道

同步通道

  • 发送者等待响应
  • 简单但可能阻塞
  • 适合：需要即时反馈
  • 示例：RPC 调用

异步通道

  • 发送后立即返回
  • 非阻塞，更高效
  • 适合：长时间任务
  • 示例：消息队列

点对点

一对一通信，隐私性好

广播

一对多通信，效率高

FORMAT

消息格式

自然语言

"请检查这个函数 是否有安全漏洞"
  • 灵活，人类可读
  • 但解析困难
  • 适合：LLM 间通信

结构化数据

{ "type": "review", "target": "auth.py", "focus": "security" }
  • 精确，易解析
  • 但不够灵活
  • 适合：工具调用

混合格式

{ "text": "请检查...", "metadata": { "type": "review", "priority": "high" } }
  • 兼顾灵活和精确
  • 最常用
  • 适合：大多数场景
SEMANTICS

消息语义

请求/响应

Request: "请分析这个代码"

Response: "发现 3 个问题..."

  • 明确的期望
  • 同步或异步

通知/事件

Event: "测试通过了"

No response expected

  • 单向通知
  • 触发后续动作

命令/确认

Command: "执行部署"

Ack: "部署完成"

  • 需要确认
  • 可能失败重试

维度选项 A选项 B适用场景
媒介直接消息共享黑板点对点 vs 协作
通道同步异步即时反馈 vs 长时间任务

DISTRIBUTED

分布式系统的经典问题

一致性问题

  • 多个 Agent 如何达成共识？
  • CAP 定理的限制
  • 最终一致性 vs 强一致性

死锁和活锁

  • 循环等待资源
  • 不断重试但无进展
  • 需要超时和中断机制

拜占庭故障

  • Agent 可能给出错误答案
  • 需要多数投票或验证

网络分区

  • 通信中断如何处理？
  • 降级策略和恢复机制
CHALLENGES

多 Agent 系统的独特挑战

协调开销

  • 通信成本可能超过收益
  • 需要最小化不必要的交互
  • 密集网状结构通常不是最佳选择

上下文压力

  • 更多通信 ≠ 更多有用信息
  • 每个 Agent 的上下文窗口有限
  • 需要智能过滤和聚合

责任归属

  • 出错时谁负责？
  • 需要清晰的审计轨迹

可调试性

  • 多 Agent 交互难以追踪
  • 需要可视化和日志工具
BLACK-BOX

黑盒 LLM 带来的挑战

不可预测性

  • 相同输入可能产生不同输出
  • 难以保证行为一致性
  • 需要冗余和验证机制

幻觉传播

  • 一个 Agent 的幻觉可能被其他 Agent 接受
  • 需要交叉验证
  • 事实核查机制

提示词注入

  • Agent 间消息可能包含恶意指令
  • 需要输入过滤和沙箱

成本累积

  • 多个 Agent 的 token 消耗叠加
  • 需要成本监控和优化
A2A PROTOCOL

A2A：Agent-to-Agent 协议

什么是 A2A？

A2A 是 Google 提出的开放协议，用于标准化 Agent 之间的通信和任务委派

核心目标

  • 标准化 Agent 发现
  • 统一任务委派接口
  • 支持长时间运行任务

关键特性

  • Agent Card 描述能力
  • 任务生命周期管理
  • 流式状态更新

适用场景

  • 跨组织 Agent 协作
  • 第三方 Agent 集成
  • 复杂工作流编排
AGENT CARD

Agent Card

Agent Card 是 Agent 的"名片"，描述其能力和接口

{ "name": "Code Reviewer Agent", "description": "专注于代码安全性和质量审查", "capabilities": ["security_audit", "code_quality", "performance_review"], "inputFormats": ["text/plain", "application/json"], "outputFormats": ["application/json"], "authentication": { "schemes": ["bearer"] }, "provider": { "organization": "Example Corp", "contact": "agent@example.com" } }
Agent Card 让 Agent 可被发现、可理解、可调用
ABSTRACTIONS

A2A 的三个核心抽象

1. Agent

具有特定能力的自主实体

  • 通过 Agent Card 描述
  • 可被发现和调用
  • 维护自己的状态

2. Task

委派给 Agent 的工作单元

  • 有明确的输入和期望输出
  • 可以长时间运行
  • 有生命周期状态

3. Message

Agent 间通信的基本单位

  • 携带任务指令或结果
  • 支持流式传输
  • 可包含元数据

MCP 标准化什么

  • tools — 可调用的、类型化的能力
  • resources — 主机可附加的可读数据
  • prompts — 可复用的交互模板
  • 一个客户端与多个服务器对话
  • 由主机（而非模型）决定暴露什么
MCP 是 Agent↔服务边界：一次工具调用，一个结果

PRINCIPLES

设计原则

1. 多 Agent 真的必要吗？

单 Agent 足够时，多 Agent 往往只增加开销和复杂度

2. 确定拓扑结构

反映任务依赖关系，最小化通信

3. 识别信息丢失点

将聚合节点视为细节可能丢失的地方

4. 识别故障隔离边界

确保系统不会停滞

密集网状结构很少是最佳默认选择。更多通信可能增加上下文压力而不增加有用信息。
