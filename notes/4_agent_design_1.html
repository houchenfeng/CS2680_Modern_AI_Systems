EDIT

工具：编辑方法

字符串替换

str_replace

  • 精确匹配旧字符串
  • 替换为新字符串
  • 适合小范围修改
  • 风险：匹配失败

行级编辑

insert / delete lines

  • 按行号操作
  • 插入/删除指定行
  • 适合结构性修改
  • 风险：行号偏移

文件重写

write_file — 重写整个文件内容，适合大规模重构，但会丢失未包含的内容

TRADEOFFS

编辑方法的权衡

精确度

str_replace 最精确，但需要完全匹配

write_file 最灵活，但可能丢失内容

安全性

str_replace 最安全，只改指定内容

write_file 风险最高，可能覆盖错误

适用范围

str_replace 适合小修改

write_file 适合大重构

没有完美的编辑方法 — 根据修改规模选择合适工具

可靠性

BEST PRACTICES

工具设计最佳实践

  • 原子性：每个工具做一件事，做好一件事
  • 类型化输入输出：明确的参数 schema 和返回格式
  • 错误处理：清晰的错误信息和恢复建议
  • 幂等性：重复调用产生相同结果
  • 最小权限：只授予必要的访问权限
  • 可观测性：记录调用日志和性能指标
QUESTION

只用 Shell 工具够吗？

Shell 的优势

  • 通用性强，几乎无所不能
  • 可以利用所有命令行工具
  • 灵活组合管道和脚本

Shell 的局限

  • 输出非结构化，难以解析
  • 安全风险高，可执行任意命令
  • 错误信息不标准化
  • 难以进行细粒度权限控制
专用工具 + Shell 组合 = 最佳方案
CONTEXT MANAGEMENT

上下文管理

Agent 的核心挑战：如何在有限的上下文窗口中放置正确的信息

上下文窗口的限制

  • Token 数量有限（通常 128K-200K）
  • 每个 turn 都要重新发送整个窗口
  • 中间位置的信息容易被忽略
  • 窗口越大，推理越慢、成本越高

管理策略

  • 准入（Admission）：控制什么进入窗口
  • 卸载（Offloading）：按需加载，不常驻
  • 转换（Transformation）：就地修剪
  • 压缩（Compaction）：最后手段

FINITE RESOURCE

上下文是有限资源

成本 Cost

每一步都要重新发送整个窗口

→ 每个 turn 都要再次付费

⏱ 延迟 Latency

更大的 prompt 需要更长的预填充和解码时间

→ 每次循环都更慢

🎯 注意力 Attention

随着窗口填满，回忆能力下降；中间部分容易被忽略

→ 更多上下文 ≠ 更好答案

FAILURE MODES

上下文失败的五种方式

命名失败模式，修复方法就变得显而易见

Poisoning

幻觉进入窗口，之后被当作事实引用

Distraction

历史不断增长，Agent 开始模仿自己过去的行为

Confusion

不相关的工具和文档将答案带偏

Clash

新信息与旧信息矛盾；两者都未解决

Drift

真正的目标被埋没，被替换为附近的子目标

Breunig, "How Contexts Fail and How to Fix Them" (2025)
